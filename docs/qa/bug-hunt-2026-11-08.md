## What held up

These checks passed on the inputs listed. They show the behaviour on those inputs; they are not proofs.

**Field icons, format (01 §4, §9):**
- **Fixture:** `v2-field-icon.vault` is version 2 (no version bump). The independent decoder finds one item with an `"icon": "key"` field, a field without the key and an `"icon": null` field. Core reads `Some("key")`, `None` and `None` (`fi01`).
- **Writer:** a core round trip keeps `"key"` verbatim, writes neither `null` nor `""`, and every decrypted ItemPlain stays canonical CBOR (`fi02`).
- **Empty string:** `""` on disk reads as `None`. `Some("")` set in memory is written as an absent key (`fi03`).
- **Hostile types:** integer, negative integer, bytes, array, map, bool, float and tagged text are each `Malformed`, with no panic (`fi04`).
- **Unknown names** are preserved verbatim through every path tried (`fi05`). The names tried include a 10,000-character name and one carrying ESC/BEL sequences. The paths:
  - `set_field` on another field and a title change.
  - A merge with the vault's own copy.
  - `change_password` and `rotate_vault_key`.
  - Delete and recover.
- **Restamp:** an icon-only change restamps that field alone, and removing an icon restamps it too. `None` → `Some("")` is not treated as a change (`fi06`).
- **Version 1 files** read the key, and `upgrade_format` keeps it (`fi08`).
- **History and strip:** `set_field` keeps the icon and pushes history as before, and a permanent delete strips fields and their icons (`fi10`).
- **Corruption:** cutting the file at every offset, and 400 random bit flips over a file with field icons, give clean errors, no panic and no silent content change (`fi11`).

**Field icons, merge (03 §5):**
- **Older icon, newer value edit:** an icon set at t=2000 loses to a peer's value edit at t=3000 made without having seen the icon, as the spec says (`fi07a`).
- **Newer icon:** the whole field wins, including the old value (`fi07b`).
- **Same-millisecond icon edits** on two devices converge in one exchange (`fi07c`). With a cloned device id they converge in one exchange and are fully equal after two (`fi15`). So the icon is part of the field's CBOR tie-break.
- **Three devices** editing icons on three different fields, one of them a removal, converge in two rounds (`fi07d`).
- **`Some("")` against `None`** settles: no further stamp movement and no reported updates (`fi16`).
- **Field reorder** persists, restamps the item, reaches two other devices and converges, with icons moving along with their fields (`fi17`).

**Field icons, sync, import/export and CLI:**
- **Conflict copies of both shapes:** a peer's later icon change in a sibling package (`fc 2.vault`) and an icon removal in an in-package `vault (Mac's conflicted copy …).bin` are both merged, written and moved to `backups/` (`fi12`).
- **Import/export:** CSV export carries no icon name, and items imported from CSV, KDBX and a hand-made 1PUX have no field icons (`fi09`).
- **CLI, Rust side (`fi13`, `fi14`):**
  - `get` prints no password and `get --reveal --ids` prints it. Neither prints raw control characters, although the icon name contains ESC/BEL, and neither prints the icon at all.
  - `edit --set`, `edit --title --tag`, `export` and `rm` keep every icon.
  - `add --help` offers no field-icon flag.
  - `vault upgrade` on a version 1 package keeps the icon.
  - `vault sync` absorbs a per-file copy with a newer icon.
- **CLI, shell side (`run_all.sh`)**, on the committed fixture:
  - `get`, `get --reveal --ids`, `edit --tag`, and a field-by-field comparison of every icon before and after the edit.
  - CSV export without the icon.
  - Twelve concurrent CLI processes adding fields to other items and to the icon item itself: nothing lost and icons intact.

**Before-write hook (03 §2):**
- **Dirty and clean saves:** it runs once per dirty save. Its change reaches disk and memory without marking the vault dirty. It does not run on a clean save, and `set_before_write(None)` removes it (`bw01`).
- **Lock:** it runs in `lock` before the Unsaved backup, and the backup carries its change. It does not run on a clean lock, on `save` while locked, or on `poll` while locked (`bw02`).
- **Restore:** it does not run on `restore_from`, and the primary afterwards is byte-identical to the backup (`bw03`).
- **Ordering:** it runs after the pre-write merge, so it sees a peer's item (`bw04`).
- **Other writes:** it does not run on idle polls. It runs on watcher merge write-backs and on per-file conflict absorption (`bw05`).
- **Expired trash:** a peer's conflict copy carrying a trashed item past 30 days reaches disk stripped when the app's sweep is the hook. A control run without the hook shows the content reaching disk, so the check can tell the two apart (`bw06`).
- **Size check:** a 65 MiB expired note makes `save` fail with `VaultTooLarge` without the hook and succeed with it, so the hook runs before the size check (`bw07`).
- **Merged reports** describe the pre-hook state: "added: 1, updated: 0" while the hook then edits every item (`bw08`).
- **Lock and unlock:** the hook survives them. A copy queued while locked is absorbed at unlock with the hook applied, and later saves still run it (`bw09`).

**2026-11-06 fixes:**
- **M1:** the write cap holds. A save, a merge write-back from a peer, and the Unsaved backup on lock are refused before any temp file is written (`rf07`, `rf15`, plus `check_vault_size` in `write` and `write_snapshot`).
- **L1:** title-only items are recoverable (`tr06`).
- **L2:** KeePass content rejected after authentication is `KdbxMalformed` (`kh04`).
- **M2 (code read):** the app's 1PUX cap is 1 GiB. Core bounds `export.data` from the central directory and while inflating, and refuses more than 10,000 entries or ZIP64.
- **L3 (code read):** the backup viewer reads through `read_package_entry_capped`, and conflict packages whose `vault.bin` is a symlink are not listed.

**vault-macos (code read only, plus the project's own main-thread test run):**

`dock.rs` sets and reads `NSApp.activationPolicy` behind a `MainThreadMarker` check and never activates the app itself.

`status_item.rs`:
- **Retain graph:** button and menu-item targets are weak. The `Target` ivars hold the item and the menu, so there is no cycle. `Inner::drop` clears every target and action before releasing the target, detaches the menu and removes the status item.
- **Callbacks:**
  - `run` retains the target, clones the callbacks `Rc`, and calls the callback with no `RefCell` borrow held. A callback can therefore drop the `StatusItem` mid-call; the project's main-thread test does exactly that.
  - Panics are caught before they unwind into Objective-C.
- **Menu:**
  - Out-of-range indices are checked before `performActionForItemAtIndex:`, which would otherwise raise `NSRangeException`.
  - A re-entrant pop is a no-op.
  - The menu is attached only for the duration of the click.
- **Ownership:** every `unsafe` block carries a SAFETY comment, and `StatusItem` is `!Send`.

The app side (`vault-app/src/status_item.rs`):
- Keeps exactly one item in a main-thread global.
- Lets AppKit callbacks only post to a channel, so an item is never dropped from inside its own callback.
- Reverts "Show Vault in Dock" to on, with the specified toast, when the installer fails.
- Updates the glyph on lock, unlock and vault switch.
- Activation goes through gpui's `set_activation_policy`. `LSUIElement` is set in `scripts/Info.plist`, and Regular is applied at startup when the setting is on.

**vault-app (code read only):**
- **Item-window hold-⌥ reveal:** the render path checks the live modifiers (⌥ alone), the window's key status and focus containment, not only the stored flag. The flag clears on deactivation and on focus-out. TOTP rows go through `render_totp`, which ignores the reveal.
- **⌘1–⌘9:**
  - The rows come from the same `counts.tags` vector the sidebar draws, so the numbering matches the display order.
  - Recently Deleted is counted only when its count is above zero, and tags only while the Tags section is expanded.
  - The keys work only on the unlocked main screen and in the main window, and they go through the unsaved-edit guard.
- **Settings** is absent from the menu and `⌘,` is a no-op unless a vault is unlocked.
- **Menu-only actions:** `MenuNextItem`, `MenuPrevItem` and `MenuCancelEdit` are unbound, so bare ↓/↑/Esc are not global key equivalents.
- **Tab into the list** selects the first row only when nothing is selected and no edit is open.
- **Save-blocked strip:** it mirrors the status line and clears on success, a clean merge, unlock, restore and close. The `KeyMismatch` and `SaveBlocked` returns in `save_locked` come before the hook, so a refused save never runs it.
- **Editor saves:** untouched fields are taken from the stored copy and changed fields carry `bf.icon`, so unknown icon names survive an unrelated edit.
- **Brand table:** compressed at build time and inflated once, with build output trusted.

**Secrets and unsafe:**
- No new `unsafe` outside vault-macos.
- No new log line or error text with secret content.
- `Field` `Debug` still redacts the value.
- The new `field_content_eq` and `same_field` comparisons of secret values are equality checks on in-memory data, not an oracle.
- Field icons are parsed only after the item's AEAD check, so nothing new runs before a key check with attacker-controlled sizes.

## Notes (spec ambiguities, not counted)

**Concurrent CLI tag edits on one item keep one tag.** Six parallel `vault edit <item> --tag tN` calls each print "updated", but the item ends with only one of the six tags. This happened on the fixture vault and on a fresh CLI vault (reproduced twice).

It follows the spec:
- 03 §5 merges `tags` as one list by its own stamp.
- The V-02 lock (03 §2) is taken before the pre-write merge, which is after the CLI computed its edit. Its stated guarantee covers lost *items*.

Concurrent edits of *different* fields or items all survive, as the 12-process check shows. Still, a script that tags in parallel silently loses work while every process reports success. If that matters for the sync lab, the CLI could:
- re-read the vault under the lock before applying its edit, or
- add tags as a set operation, not by list replacement.

To reproduce:

```
for i in 1 2 3 4 5 6; do vault --vault X.vault --password-env P edit Item --tag t$i & done; wait
vault --vault X.vault --password-env P get Item
```

**Field order has no stamp.** A drag-to-reorder alone persists and propagates (`fi17`). But because order follows "whichever item has the greater `modified_at`" (03 §5), the reorder is lost if another device makes any later edit to the same item before it syncs. Neither 03 §5 nor 05 §2.5 says how field order merges, so this should be written down if it is the intended behaviour.

**"Settings…" after an auto-lock with no window.** PROGRESS records this as a known corner: with the window closed, an auto-lock leaves the menu item in place until a window opens. It is inert, because `open_settings` refuses while locked. 05 §2.5 speaks only of the Choose and Unlock screens, so this is not a deviation. The status item's "Unlock…" reopens the window, which rebuilds the menu.

**1PUX EOCD scan.** `check_zip_entry_count` checks every EOCD signature candidate in the last 64 KiB. If a real archive's central directory is small, that window reaches into compressed attachment bytes, and a random `PK\x05\x06` with a plausible comment length and a large count field would refuse a valid archive. By estimate this is on the order of one archive in 10^5–10^6. It was not provoked.

**Field icon names have no length cap.** A 10,000-character name round-trips. The name is inside the item's AEAD and under the 64 MiB file cap, so this is not a pre-authentication issue. The app's editor can only pick names from the 40-symbol list.
