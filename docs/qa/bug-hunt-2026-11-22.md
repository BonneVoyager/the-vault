## Summary

The run found three low-severity issues and no high or medium ones. Every earlier ledger check still passes: 314 Rust checks and 147 CLI checks.

1. **L1: a vault named `conflict` loses its backup policy and retention.** The backup-name parser tries the `conflict-` prefix first, so this vault's own snapshots are mis-read:
   - the plain snapshot is not listed at all;
   - `-2`, `-3` and `-unsaved` snapshots are listed as Conflict copies.

   As a result, every save takes a snapshot (the app autosaves 2 s after each edit) and none is ever pruned.
2. **L2: the CLI hides a skipped backup.** When `backups/` is a symlink, `vault add` (and every other mutating command except `sync`) exits 0 with no message. vault-sync emits `Error("backup failed: … is a symlink …")`, but the CLI never subscribes outside `sync`. 03 §2 D-1 says "never a silent fallback".
3. **L3: restore discards edits that are in the vault but not yet on disk (code read only, library evidence).** `restore_from` documents "Unsaved edits are discarded". The app neither saves nor writes an Unsaved copy before calling it. Edits are lost whenever saves are failing at the time: a busy lock, a foreign file on disk, or a too-large vault. Lock, by contrast, preserves them.

**The focus areas held on these inputs** (details under "What held up"):
- The retention multiplier gives the 05 Settings numbers: a daily tier of 15/30/60/120 days, and monthly for about 18 months / 3 / 6 / 12 years.
- Clamp, NaN and ±inf behave as 03 §8 says. Unsaved and Conflict backups (file and package) are never pruned.
- `restore_from` refused every damaged backup (each cut offset and 300 bit flips), and every symlink, FIFO and oversized backup. The primary stayed untouched each time.
- Eleven special conflict-entry shapes are each reported once, left in place, never followed, and re-reported after lock/unlock.
- `save_blocked()` survives lock and unlock, and clears once a readable file returns.
- A restored snapshot brings expired trash back, and the next write with the app's sweep hook strips it again.

## Findings

### L1: A vault named `conflict` snapshots on every save and never prunes

**Fixed 2026-11-22**: `parse_file_name` tries the snapshot name first and falls back to the conflict name; tests in vault-sync (`a_vault_named_conflict_reads_its_own_snapshots`, `tests/backups.rs`).

- **Severity:** low. The trigger is narrow, but the effect is unbounded growth.
- **Where:** `crates/vault-sync/src/backup.rs:200-202` (`parse_file_name`). The effect shows in `crates/vault-sync/src/synced.rs:752-765` (`maybe_backup`'s `newest`) and `backup.rs:393-400` (`apply_retention`).
- **Expected:**
  - 03 §4: "Take a snapshot if no snapshot exists newer than **1 hour** …" and the retention tiers ("delete the rest").
  - 03 §8: "Retention prunes `Snapshot` only; `Unsaved` and `Conflict` are never pruned."
  - 03 §9: "Save twice in 1 s → one backup."
  - Snapshot names are `<name>-<UTC ISO8601 …>.vault.bin` (`-2`, `-3`, `-unsaved`). Conflict copies are `conflict-<timestamp>-<original name>` (03 §6).
- **Observed:** for a package `conflict.vault`, every name starts with `conflict-`, so the conflict branch claims it first:
  - `conflict-<stamp>.vault.bin`: line 202's `strip_prefix('-')?` returns `None` from the whole function, so the file is **not listed at all**.
  - `conflict-<stamp>-2.vault.bin` and `conflict-<stamp>-unsaved.vault.bin` are listed as `BackupKind::Conflict`.

  So `maybe_backup` finds no Snapshot and takes one on every save. `bk11` measured this against an `ordinary.vault` control:

  | Vault | Extra snapshots from 5 saves within one hour | Files in `backups/` before → after retention |
  |---|---|---|
  | `ordinary.vault` | 0 | 61 → 22 |
  | `conflict.vault` | 5 | 66 → 67 (nothing pruned) |

  Settings lists only the `-N` files, labelled "Conflict copy from …".
- **Why it matters:**
  - The app autosaves 2 s after each edit, so each edit session writes one full vault copy per save into `backups/`, and none is ever removed.
  - `backups/` is in the synced package (03 §1), so a cloud folder fills with copies the user cannot see in Settings.
  - "conflict" is an odd vault name, but nothing refuses it.
- **Reproduction:** `cd qa/spec-checks && cargo nextest run --no-fail-fast --test backups_1122 bk10 bk11 --no-capture`
- **Suggested fix:** in `parse_file_name`, do not return early from the conflict branch: on any mismatch, fall through to the snapshot parse. When `name` is `conflict` (or whenever the snapshot parse succeeds for `name`), prefer the snapshot reading. Simpler: give conflict entries a prefix that cannot be a vault name followed by a stamp, keeping the old prefix readable. Add a fixture-style test with a package named `conflict`.

### L2: CLI commands other than `sync` drop the "backup failed" report (symlinked `backups/`)

**Fixed 2026-11-22**: `save_and_warn` subscribes before each save and prints `SyncEvent::Error` as sanitised `warning:` lines on stderr, exit code unchanged; tests `add_warns_when_backup_fails`, `add_without_problems_is_silent_on_stderr`.

- **Severity:** low.
- **Where:** `crates/vault-cli/src/main.rs:914` (`add`). Also the saves at `:719` (attach add), `:760` (attach rm), `:1011`, `:1073` and `:1139`. None of these subscribes to the `SyncedVault` events. Only `sync` (`:1018`) does.
- **Expected:**
  - 03 §2 D-1: "`backups/` and `attachments/` must not be symlinks … a symlink or special file is `UnsafePackageEntry`, never a silent fallback".
  - 03 §4: every CLI process's save is "the first save after unlock", so it must snapshot.
- **Observed:**
  - With `backups/` replaced by a symlink, `vault add` writes the item, takes no snapshot (correct: nothing is written through the link), exits 0, and prints only the new id.
  - The library does report it: `bk09` sees `Error("backup failed: …/backups is a symlink or not a directory; refusing to use it")` after an `Ok` save.
  - Reproduced in `run_all.sh` run 2 and by hand.
- **Why it matters:** the CLI is the phase-1 deliverable and a scripting tool. A script user gets no sign that backups stopped. The same applies to any other snapshot failure: a full disk, a permission error, a backup over 64 MiB.
- **Reproduction:**
  ```sh
  cargo build -p vault-cli
  T=qa/spec-checks/tmp/l2; mkdir -p $T; export MPW='tidy-Walrus-orbit-Velvet-42' V=target/debug/vault
  $V --vault $T/a.vault --password-env MPW init --kdf-test-params
  $V --vault $T/a.vault --password-env MPW add --title one
  mkdir $T/else; mv $T/a.vault/backups $T/real; ln -s "$PWD/$T/else" $T/a.vault/backups
  $V --vault $T/a.vault --password-env MPW add --title two; echo rc=$?   # rc=0, only the id printed
  ls -A $T/else                                                          # empty: no snapshot anywhere
  rm -rf $T
  ```
- **Suggested fix:** subscribe in `open_synced`. After each `save()`, drain the receiver and print `SyncEvent::Error` lines to stderr as warnings (sanitised with the existing `sanitize_line`). Keep the exit code unless the save itself failed. Assert the warning in a CLI test.

### L3: Restore discards edits that are not yet on disk (code read only, library evidence)

**Fixed 2026-11-22**: `restore_from` preserves the in-memory vault as an Unsaved backup under `lock`'s condition (`must_preserve`: dirty, key mismatch, save blocked or missing primary) before anything changes; a failed Unsaved write refuses the restore. 03 §4/§8 aligned. N1, N3 (spec and help wording) and N8 (labels through `sanitize_label`) also addressed.

- **Severity:** low.
- **Where:**
  - `crates/vault-app/src/state/sync.rs:613-640` (`restore_backup`): `guard` only handles an open edit buffer; there is no `save()` or Unsaved copy before `restore_from`.
  - `crates/vault-sync/src/synced.rs:905-925`: the doc comment says "Unsaved edits are discarded".
- **Expected:**
  - 03 §4: "'Replace current vault with this backup' (which first snapshots the current one)".
  - 03 §8 `lock`: "unsaved edits are snapshotted to an Unsaved backup first; the outcome says … so the app never claims edits were kept when they were not".

  03 §8's `restore_from` sentence says "snapshots the current *file* first", so the library matches its own paragraph. The user-facing action in §4 promises the current vault.
- **Observed:**
  - `rs02`: an item added through `edit` but not saved, then `restore_from` → the item is in neither the restored vault nor any backup.
  - In the app, committed edits reach disk by the 2 s autosave, so the gap is the time while saves fail, for example:
    - a busy lock or `PrimaryChangedDuringSave` (one scheduled retry);
    - `SaveBlocked(ForeignVault)`, where `restore_from` proceeds because the foreign primary parses;
    - `VaultTooLarge`, the strip's own case.

    A user who restores to get out of such a state loses those edits with no Unsaved copy. Lock in the same state keeps them (`sb02`, `bk07`).
- **Why it matters:** this is the one remaining path where the app drops committed edits with no copy and no warning. Lock and quit were closed against it earlier.
- **Reproduction:** `cd qa/spec-checks && cargo nextest run --no-fail-fast --test backups_1122 rs02 --no-capture` prints `INFO restore_from while dirty: unsaved edit kept somewhere = false`. The app half is from reading `restore_backup`.
- **Suggested fix:**
  - In vault-sync, make `restore_from` write the dirty in-memory vault as an `Unsaved` backup before replacing the file, as `lock` does (and report `Unpreserved` when that is impossible). Or have the app call `save()` first and, if it fails, ask before discarding.
  - Align 03 §8's sentence with whichever is chosen.

## What held up

These are observed behaviours on the inputs used, not proofs.

- **Retention at 1× (`bk01`), over 2,194 planted snapshots spanning 13.5 years:**
  - everything under 24 h is kept;
  - one per calendar day to day 30;
  - roughly weekly after that;
  - monthly to about 3.15 years;
  - 12-year-old Unsaved, Conflict-file and Conflict-package entries are kept.
- **Retention at 0.5×, 2× and 4× (`bk02`):**
  - the daily tier runs 15, 60 and 120 days, the Settings labels;
  - the oldest kept snapshot is 1.48, 6.32 and 12.81 years old, against the hint's 18 months, 6 years and 12 years.
- **Clamp (`bk03`):** 0.1, −1, −0.0 and −inf act as 0.5; 10 and +inf as 4.0; NaN and "never set" as 1.0. Kept sets are identical in each pair.
- **Snapshot names (`bk04`, `bk05`):** same-second `-2`/`-3` files are retention-aware.
  - Hostile names (impossible dates, 20-digit fields, `:` separators, a far-future year) do not panic `backup_now` or `backups()`.
  - A non-snapshot file (`notes.txt`) is never deleted.
- **Hourly policy (`bk06`):** the hourly snapshot is taken when the newest is 2 h old. A snapshot dated 3 days in the future does not suppress it.
- **Backups disabled (`bk07`):** no automatic snapshots. `backup_now`, the pre-restore snapshot and the Unsaved copy at lock still happen.
- **Snapshot files (`bk08`):** `backup_now` ×4 in one second gives unique `-N` names, exact primary bytes, mode 0600.
- **Restoring every listed kind (`rs01`):** Snapshot, Unsaved, Conflict file and absorbed Conflict package all restore.
- **Damaged backups (`rs03`):** of 1,241 damaged backups (every cut offset plus 300 single-bit flips), 1,240 were refused, with the primary and the in-memory vault unchanged each time.
  - The one that opened is a flip inside the header's `created_at`, the vault creation time.
  - 01 §4 leaves that field outside every AEAD and the header digest (00 lists it as an accepted plaintext leak), and the items were intact.
  - The check was fixed during the run to go on past the first input that opens, so all 1,241 inputs ran.
- **Special backup entries (`rs04`):** symlink, dangling link, FIFO, empty conflict package, conflict package with a linked `vault.bin`, and a 65 MiB file are all refused within the time limit, with the primary untouched.
- **Restore with peers (`rs05`):** three handles converge after a restore on one of them (see Note N3 on what survives).
- **Restore across a password change (`rs06`):** an old backup restores with its own (old) password. The new password is `WrongPassword`. The vault then opens with the old password.
- **Trash versus backups (`tb01`, `tb02`):**
  - A restored snapshot holding trash past 30 days puts the content back on disk, as 03 §2 allows ("writes the backup bytes as they are").
  - A peer's next write with the sweep hook strips it, and so does this handle's next write.
  - The app's `restored()` runs `expire_trash()` and schedules the save (code read).
  - A permanently deleted item returns *into the trash* from a snapshot taken during its window.
- **Save-blocked (`sb01`–`sb03`):**
  - `save_blocked()` is `NewerVersion(3)` at detection, while locked and after unlock; a save is still refused.
  - It clears after the peer restores a readable file.
  - A foreign primary plus lock/unlock reopens *our* vault (last readable copy) with `ForeignVault` still reported, and the unsaved edit is in the lock's Unsaved copy.
  - In the app, `unlocked()` clears and then re-raises from `save_blocked()` on the shared unlock path (code read).
- **Special conflict entries (`sp01`):** a socket, a directory named `vault 2.bin`, dangling and looping links, links to `/dev/zero` and to a FIFO, a FIFO sibling, and siblings whose `vault.bin` is a FIFO, a directory or a link to `/dev/zero`:
  - each gives exactly one `UnreadableConflict` naming it;
  - none is followed, absorbed or moved, and the primary is untouched;
  - nothing hangs.
- **Special entries over time (`sp02`, `sp03`, `sp04`):**
  - A link replaced by a regular copy at the same path is absorbed.
  - Entries are re-reported after lock/unlock, including one first seen while locked.
  - A sibling with a symlinked `attachments/` is refused with an error, nothing is published through the link, and the outside folder is untouched.
- **Deleting and listing (`db01`, `bl01`):**
  - `delete_backup` on links to the primary, to an outside file and to an outside directory refuses all three (`NotABackup`), and the targets survive.
  - `backups()` and the viewer's `read_package_entry_capped` do not hang on FIFOs, and refuse links.
- **CLI:**
  - `vault sync` with each special entry exits 1 with "not converged", leaves the entry and keeps `vault.bin` byte-identical.
  - 10 concurrent `add`s all survive, with no tmp file left; all 11 backups open with the master password and are 0600.
- **Viewer (code read only):**
  - It reads through the no-follow capped reader and clears the password from the input.
  - It drops the decrypted backup if the live vault locked during the unlock, and binds every read to `session_gen`.
  - "Copy to current vault" inserts a clone under a fresh id with `deleted_at` cleared, so it never overwrites the live item.
  - The prompt refuses plain copy.
- **Settings (code read):**
  - The retention labels and hint are computed as `round(30·m)` days and `round(36·m)` months.
  - `settings.json` values outside {0.5, 1, 2, 4} fall back to 1.0.
  - Changes apply to the open vault immediately.
- **Security pass (step 4):**
  - no `unsafe` outside vault-macos;
  - the secret equality checks in `merge.rs`, `kdbx.rs`, `edit.rs` and `editor.rs` compare the user's own values for dedupe and merge, not authentication;
  - vault, blob, lock and snapshot files are 0600 and the package and `backups/` 0700;
  - the new sanitising of conflict names in the app covers C0, C1, bidi and invisible format characters;
  - the backups listing uses `lstat` and never lists a linked entry;
  - every path that parses an attacker-supplied backup is capped at 64 MiB, and its KDF is range-checked before Argon2.

## Notes

These are spec ambiguities and observations. They are not counted as bugs.

- **N1. The multiplier scales every tier, including "keep all from the last 24 h".**
  - 03 §4 says only "the retention multiplier". The code (`retain`, documented there) scales the keep-all window too (48 h at 2×, 96 h at 4×), as well as the weekly tier (12 weeks × m) and the monthly cap (`round(36·m)`).
  - 05's hint matches the result. Consider one 03 §4 sentence naming what scales.
- **N2. A plain file named like a sibling package (`<name> 2.vault`) is skipped without a report.**
  - `sp05`, and the `run_all.sh` INFO line: `vault sync` exits 0 with "0 conflict copies absorbed".
  - The code does this on purpose (`reconcile.rs:455`: "a plain file is the unsupported single-file layout").
  - 03 §6 step 1's "is not a regular file / directory (symlink, FIFO …) → UnreadableConflict" can be read to cover it, since a file where a package directory belongs is "not a directory". Decide and word 03 §6 accordingly.
- **N3. "Replace current vault with this backup" is undone on other devices for anything changed after the backup.**
  - `rs05`: right after the restore, a deleted item is back on the restoring handle. Once two peers merge, it is deleted again on disk, because the tombstone is newer.
  - This follows 03 §5, but 03 §4 and 05 do not say it. A user who restores to undo something on a two-Mac setup will see it undone again. Worth a sentence in 03 §4 and in `docs/help.md`.
- **N4. The retention multiplier is per app, but `backups/` is shared.**
  - Each device runs retention over the same synced folder with its own setting, so a device at 0.5× prunes what a device at 4× keeps.
  - This is inferred from the code (`apply_retention` over `list_backups` of the package) and not run with two handles.
- **N5. Snapshots of a renamed package (`old-<stamp>.vault.bin`) are invisible to `backups()` and never pruned,** because the parser requires the current name (code read).
- **N6. Unsafe entries share one content key (`UNSAFE_ENTRY`).** A symlinked `vault 2.bin` swapped for a FIFO at the same path is not reported a second time (code read).
- **N7. "Copy to current vault" copies the whole item under a fresh id** (code read only): password history, removal markers, per-attribute stamps and attachment references come along. Blobs that are still present are shared by both items, and orphan cleanup keeps them while either refers to them. Nothing is lost; 05 does not say what is copied.
- **N8. Read-mode labels now print the stored name exactly** (`56f59d6`, per 05). Names are still not passed through `sanitize_line`, so a bidi override or control character from an imported CSV/1PUX/KDBX field name reaches the label. This predates the commit (code read only).
- **N9. Absorbed conflict copies keep trashed content past 30 days indefinitely,** since Conflict backups are never pruned. This is covered by 03 §1.1's "Snapshots are not scrubbed" and listed only so the trade-off is visible.

## Limits

- **vault-app and vault-macos were not driven.**
  - The viewer, Settings, restore flow, label and strip statements are code read only. No GUI was run.
  - L3's app half is inferred from `state/sync.rs` and `state/edit.rs`; its library half was measured by `rs02`.
- **Timing-based checks ran on one Mac with `NoopHooks`.** These are the watcher checks (debounce 500 ms, waits of 3–8 s) and `sp01`'s 11 shapes at about 5 s each.
- **Retention was checked against planted snapshot names relative to the wall clock.** Calendar-day and week boundaries near midnight UTC could shift a bucket by one. The assertions allow ±2 days and widened year bounds for that.
- **Not run:**
  - fuzzing (no format or importer change in this wave);
  - `cargo deny` and `cargo audit` (no manifest or lockfile change);
  - real iCloud Drive, Dropbox or Syncthing folders;
  - two devices with different retention settings (N4).
- **Test-time KDF parameters were used throughout.**
- **Temporary files went under `qa/spec-checks/tmp/`,** and each check removes its own. The run's logs (`ledger-run*.log`, `cli-run*.log`, `ws-*.log`) are removed at the end of the run.
- **Nothing outside `qa/` and `docs/qa/` was modified.** Nothing was staged or committed.
