## Summary

There are no high or medium findings. The areas that changed in this wave held on every input tried:

- NFC/NFD path comparison, conflict copies of both shapes under either spelling, and `delete_backup` with hostile paths.
- `WaitingForBlobs`: emitted once, never while locked, and re-checked at unlock without a watcher.
- The merge-only cap for `removed_attachments`.
- Per-attribute stamps on three devices.
- Commutativity, convergence within N rounds, monotone stamps, and guarantee 9 with resurrection.

There is one low code finding. Merge is not idempotent when an item's attachment references are not already in merge order (`added_at`, then `id`). Merging a vault with an exact copy of its own file then reports an update and bumps `modified_at`. Two attachments added in the same millisecond are enough to trigger it, so no clock skew is needed. The state settles after one extra write per device, with no endless ping-pong.

There is one low documentation finding. 01 §4 still says `removed_attachments` is "cap 64 newest", but 03 §5 now caps markers only in a merge, and only those whose reference neither side holds.

All earlier findings are fixed:

## Findings

### L1. Merging a vault with a copy of its own file changes it when attachment refs are out of merge order

- **Severity:** low
- **Where:** vault-core.
  - `crates/vault-core/src/vault.rs:944`: `add_attachment_ref` appends the ref (`item.attachments.push(r)`).
  - `crates/vault-core/src/vault/merge.rs:438`: `merge_live` sorts the union by `(added_at, id)`.
  - `crates/vault-core/src/vault/merge.rs:690-718`: `item_eq` compares `attachments` element by element, in order. A merge that only reorders refs therefore counts as a content change.
  - `crates/vault-core/src/vault/merge.rs:206`: that change is stamped `modified_at + 1`.
- **Expected:**
  - 03 §3: "Merge is idempotent and commutative, so a ping-pong between two devices converges in one round trip each."
  - 00 roadmap item 2 lists "idempotence" among the merge laws.
  - 03 §5: "`attachments` are merged by union on `id` (sorted by `added_at`, then `id`)".
- **Observed:**
  - **Simple trigger:** two refs added to one item in the same millisecond carry the same `added_at`. If the second has the smaller id, the local order is not the merge order. `x.merge_from(copy of x's own file)` then returns `updated: 1` and raises the item's `modified_at` by 1. The same happens when a later add carries an earlier `added_at` (a clock that went back).
  - **Seeded scripts:** in the 80 two- and three-device scripts, seeds 58 and 75 hit this through ordinary adds under a skewed clock, in both runs. Every one of the 15 self-merge changes seen over 300 debug seeds differed only in `attachments`.
  - **Not affected:** commutativity, convergence within N rounds, monotone stamps and guarantee 9 held on the same scripts.
- **Why it matters:**
  - Every pre-write merge, watcher merge or conflict absorption over such an item reports a change and causes one extra write and backup decision, even when nothing changed.
  - It breaks a stated law, which other reasoning relies on, for example "the other device will merge it idempotently" (03 §3 step 6c).
  - Two app windows dropping several files at once is enough; no clock skew is needed.
  - Impact is bounded: with two watching handles the state settled after one exchange each, and `vault.bin` stayed byte-stable afterwards (`sw07`).
  - The project's property test does not catch it. Its generator has no attachment operations, and its idempotence law is `(x<-y)<-y`, not `x<-x`.
- **Reproduction** (reproduced twice):
  ```sh
  cd qa/spec-checks
  cargo test --test merge_laws ml08   # two refs, same added_at, descending ids: self-merge reports updated 1
  cargo test --test merge_laws ml07   # second ref with an earlier added_at
  cargo test --test merge_laws ml01   # seeded scripts; seeds 58 and 75
  cargo test --test sync_nfc sw07     # through two SyncedVault handles: settles, no ping-pong
  ```
- **Suggested fix:** keep `attachments` in the canonical order everywhere, not only in the merge. Insert in `(added_at, id)` order in `add_attachment_ref`, and normalise the order in `insert`, `update` and on read. Alternatively, compare attachments as a set keyed by id in `item_eq`, but then two devices can still serialize different orders. Add attachment add/remove operations and an `x <- copy(x)` law to `merge_props.rs`.

### L2. Spec 01 §4 still describes a plain "cap 64 newest" for `removed_attachments`

- **Severity:** low (documentation)
- **Where:** `specs/01-vault-format.md:112`. The `removed_attachments` line reads "tombstones so a removal survives merge, cap 64 newest, purged with item tombstones".
- **Expected:** `specs/03-sync.md:115` (2026-11-01) says markers "are never dropped by a local removal; a merge caps them at 64 by dropping, oldest `removed_at` first, only markers whose reference neither side still holds". The `removed_fields` line in 01 §4 at least points to 03 §5.
- **Observed:** the implementation follows 03, which is correct:
  - 80 local removals keep 80 markers.
  - A merge keeps every marker whose ref either side held, including when more than 64 are held.
  - A merge drops only unreferenced ones, oldest first (`ml05`, `ml06`, `m12`).

  A reader implementing from 01 alone would truncate on every removal. That is the behaviour this wave removed, and it lets a removed ref, whose blob may already be pruned, come back.
- **Why it matters:** 01 is the format spec a second implementation reads first.
- **Reproduction:**
  ```sh
  grep -n "removed_attachments" specs/01-vault-format.md specs/03-sync.md
  ```
- **Suggested fix:** change the 01 §4 note to "newest first; capped at 64 only by a merge, and only over markers whose reference neither side still holds (03 §5)".

## What held up

Each item held on the inputs tried. That shows the behaviour on those inputs, not a proof.

- **Merge laws (00 roadmap item 2), own generator:** 80 scripts of 45 steps on two and three devices. The operations were insert, set by id and by name, add, rename and remove fields (duplicate and empty names, sections), title, favorite, tags (including reorders), icon, add and remove attachment refs, delete, and pulls. Clocks included backwards jumps and exact cross-device ties. Each ItemPlain was decrypted independently.
  - **Commutativity:** content was equal after one exchange with `modified_at` within 1 ms, and byte-equal after two.
  - **Idempotence of `(x<-y)<-y`:** held, and its report showed nothing changed.
  - **Convergence:** N devices were byte-equal after N simultaneous rounds and stayed fixed after one more round.
  - **Monotonicity:** item `modified_at`, and while live every attribute stamp and field stamp, never decreased after any edit or merge.
  - **Exception:** `x<-x` idempotence fails as described in L1.
- **Guarantee 9 and resurrection:** on 40 random converged states:
  - A delete survived a merge with an older copy.
  - A strictly later edit on another device resurrected the item on both devices.
  - A later delete beat an older edit.
- **Per-attribute stamps (03 §5):** title on A, favorite on B, icon on C, and a tag reorder on A all survived on three devices, in three pull orders.
- **`removed_attachments` cap (03 §5, 2026-11-01):** local removals never drop markers. When one side holds the 10 oldest removed refs, both merge directions keep their markers, drop the refs and cap at 64. When 70 removed refs are held, all 70 markers stay and the 10 unreferenced ones go. Devices converge without any ref coming back. A removal on one handle also survives another handle's later save.
- **NFC paths (03 §3):**
  - A package stored in NFD under an NFD parent and opened through the NFC spelling, and the reverse, merged primary changes both ways. It was never treated as its own conflict copy.
  - The parent directory's raw name bytes were unchanged.
  - An in-package `vault 2.bin` and a Dropbox-style copy with a decomposed host name were absorbed into `backups/`.
  - Sibling packages `CAFÉ 2.vault` (upper case, NFD) and `Café (Zoë's conflicted copy …).vault` (NFD) of `Café.vault` were absorbed. Only the package remained, with its stored name.
  - The CLI's `sync` absorbed an NFD sibling.
- **`delete_backup` (03 §8):**
  - Accepted through an NFD spelling: a snapshot, an absorbed conflict package and an `Unsaved` backup (deleted while locked), each emitting `BackupDeleted`.
  - Refused, with the primary, the backups dir and outside files intact: the primary (NFC and NFD), `backups/../vault.bin` (NFC and NFD), the backups dir, the package dir, another package's backups, and `backups/../../file`.
  - A symlink in `backups/` pointing at the primary never removed the primary.
- **`WaitingForBlobs` (03 §6 step 4, §8):**
  - Emitted once, naming the conflict path, after the step-3 merge, despite three more events on the waiting package and three saves of our own. `ConflictAbsorbed` followed the blob.
  - Never emitted while locked.
  - A package still waiting at lock was absorbed at the next unlock after `stop_watching`, with no watcher.
  - Per-file copies never wait.
  - It re-fires after unlock and after stop/start watching, which the spec allows.
- **Hostile authenticated payloads:**
  - Attribute stamps given as text, negative, float, bytes or map, and `removed_attachments` given as text, without an id, with a 3-byte id or with a text stamp, were all `Malformed` without a panic.
  - 200k markers loaded, edited, merged and capped to 64 in 5.4 s in a debug build.
  - Stamps at `u64::MAX` did not panic on edit, set, remove, delete, attach or the equal-stamp merge bump, and the results reopen.
- **Corruption sweep on a file with every new key:** the file carried attribute stamps, attachment markers, field markers, refs, history, an icon and an enclave slot.
  - Every cut offset failed cleanly.
  - 800 seeded multi-bit flips never opened with changed contents, on the password path or the `unlock_with_key` path, and never panicked.
- **CLI:**
  - `edit` changed title, favorite, tags and untags.
  - `--set-env` stores the value without echoing it, and a missing variable gives a clean error.
  - Two same-named fields can be added, and a `--set` on the shared name is refused with the file byte-identical.
  - `--rm-field` by id removes exactly one field and writes a `removed_fields` marker. `--set` keeps field ids.
  - Unknown kinds, unknown ids and a malformed `--icon` exit cleanly.
  - A malformed `VAULT_DEVICE_ID` is refused with nothing written. A valid one applies to that process only, and the stored id is stable.
  - Concurrent writers lost nothing:
    - 10 concurrent `edit --add` on one item.
    - 15 mixed concurrent `add`, `edit` and `sync` processes.
  - `sync` absorbed both conflict shapes into `backups/` and left a foreign vault named `<name> 3.vault` alone. It merged a blob-waiting sibling but did not move it.
- **Ledger:** all 144 earlier checks pass. They cover format, tamper, keys, header merge, field ids, upgrade, sync, both conflict shapes, backups and retention, attachments, TOTP and the generator against independent HMAC, importers including hostile KDBX headers, modes, and 12 concurrent CLI writers.
- **Security read (step 4):**
  - **Notes reference resolver** (`crates/vault-app/src/screens/main/notes.rs:213-675`, code read only):
    - Every byte-level slice is taken at an ASCII delimiter, and label scans use `char_indices`, so a multi-byte character cannot split a slice.
    - Label scans are bounded at 999 bytes and stop at the next bracket.
    - Backtick runs and parentheses are prebuilt tables with binary-search lookups, and the `![` escape check counts disjoint runs. No quadratic path was found.
    - Only definitions whose destination passes `is_web_link` are rewritten.
    - A crafted destination containing `)` or `](javascript:…` can change how the rewritten text parses, but every link node is re-checked with `is_web_link` before it is clickable, and images never load.
  - **Touch ID** (`crates/vault-macos/src/biometric.rs:251-262`, `:476-488`, code read only):
    - It compares `domainState.biometry.stateHash` for equality only.
    - A nil hash counts as changed, and an item without a stored state forces re-enrolment.
    - The check runs before the prompt.
    - The `unsafe` blocks carry `SAFETY` comments.
  - **vault-sync:**
    - NFC folding is used only for comparison and bookkeeping keys (`package.rs:74-120`, `watch.rs:56-246`). File operations use the event's or caller's spelling.
    - `delete_backup` canonicalizes only the parent, never follows the entry, and requires a listed backup name (`synced.rs:766-830`).
  - **Crate-wide:**
    - vault-core and vault-sync still `forbid(unsafe_code)`.
    - Nonces and keys come from `OsRng`.
    - The new error texts name keys and positions, never values.
    - The new parsing of attribute stamps and markers runs only after item decryption.

## Notes

None of these are counted as bugs.

- **Builders edited the QA ledger:**
  - a7d7a22 rewrote `qa/spec-checks/tests/merge.rs` `m12_tombstone_caps` to the amended 03 §5 rule. The new assertions match the spec text.
  - 215a0f9 reformatted the ledger. It removed and re-added the same number of `assert` lines (246), and spot checks found every removed assertion message still present.

  No check was weakened. Keeping the ledger independent works better when builders leave `qa/` to the hunter, or at least flag such edits in the commit message.
- **"Round" in the merge laws:** 00 item 2 does not define a round. This run used simultaneous rounds, where everyone reads every file first and then merges in order. All-pairs sequential pulls (`m10`, `mi09`) also converge.
- **Marker cap cost under hostile input:** `cap_tombstones` removes with `Vec::remove` while scanning from the end (`merge.rs:589-603`), and the droppable test calls `Item::attachment`, which is linear. An item with very many markers interleaved with very many still-held refs is therefore quadratic in a merge. Only a vault-key holder can write that. 200k markers with no refs took 5.4 s in a debug build.
- **`removed_history`:** not exercised by the property scripts. No public operation for deleting a history entry was found from the spec's API list.
- **`WaitingForBlobs` re-firing:** it fired again after unlock (`sw02`) and after `stop_watching`/`start_watching` (`sw04`), which 03 §6 allows. A plain own save never re-raised it.

## Limits

- **Platforms not driven:** vault-macos and vault-app were not driven. Touch ID, the notes renderer and the reference-link resolver are code read only. Keychain, pasteboard and iCloud were not exercised.
- **API discovery:** API shapes came from the spec, `--help`, the earlier ledger and compiler errors. Implementations were read only in step 4.
- **Watcher timing:** sync checks rely on FSEvents with a 500 ms debounce on one local APFS volume, which is normalisation-insensitive. The accepted edge in 03 §3 (a volume that keeps NFC and NFD names as distinct files) was not tested. Real cloud providers, network volumes and eviction were not tested.
- **Randomised checks:** random scripts and bit flips use fixed seeds, while device and item ids are random per run. This is not fuzzing.
- **Not tested:** KDBX 3 import, passkey slots (not implemented), the 0.5×–4× retention multipliers, and the provider-label classifier.
