# Bug hunt 2026-11-27

Baseline: commit `4b21cc0` on `main`, clean working tree. Previous hunt: `docs/qa/bug-hunt-2026-11-22.md`
(baseline `389142a`). Since then seven security-review waves landed (`docs/qa/security-review-2026-11-26.md`):
format version 3, symmetric merge restamp and header merge guard, authenticated backup retention, Unsaved
fallback copies and package Repair, attachment quarantine, the freshness anchor, importer caps, the KDF floor,
the TOTP period cap, CLI reveal escaping, the non-modal file panel and the sleep-aware idle lock.

Order of work followed the agent definition: specs `00`–`05` and the README first; new checks written in
`qa/spec-checks/` before any source, test or progress file was opened; everything run (failures reproduced at
least twice); then the security read of the source; then this report. The security review report was read
only in step 4.

## Summary

No high or medium findings. Two low findings, both reproduced at least twice:

- **L1**: `vault get --reveal` leaves many Unicode format (Cf) characters raw, although the command's help
  promises they are escaped. Among them are U+00AD SOFT HYPHEN and the invisible TAG block
  (U+E0001, U+E0020–U+E007F).
- **L2**: spec 04's dependency list for vault-macos omits `block2`, which the new non-modal file panel uses.

The new format 3 held up under every check written for it. Checks covered every bit of a v3 file on the key
path and every header byte on the password path, every cut, duplicate keys, relabels, record-level unknown
keys from a newer writer, and the full tamper map on both unlock paths.

Guarantee 6 also held: the restamp rule was checked on 820 merges over 60 random 2- and 3-device scripts.
So did the header merge guard, authenticated retention (forged-body and rotated-key snapshots), the Unsaved
fallback, `repair_package`, quarantine restore, the freshness surface, and all importer caps (including a
ZIP64 directory and a KDBX gzip bomb).

The project's own suite is green. Eleven spec ambiguities and drifts are listed under Notes and are not
counted.

## Findings

### L1: `vault get --reveal` prints most Unicode format characters raw

- **Severity**: low
- **Crate and location**: vault-cli, `crates/vault-cli/src/main.rs:345-356`. The `sanitize` match arms are a
  hand-written list. The help text is at `main.rs:84-85`.
- **Expected**: the documented contract of `vault get --help` (the CLI's specs give no other rule for
  revealed output) is: "Print secret values. Revealed values are escaped reversibly: a backslash prints as
  `\\`, a tab as `\t`, other control and format characters as `\u{XXXX}`."
- **Observed**: a password field holding every code point Python's Unicode tables class as Cf (format) was
  revealed with these left raw:
  - U+00AD
  - U+0600–0605, U+06DD, U+070F, U+0890–0891, U+08E2
  - U+110BD, U+110CD, U+13430–1343F, U+1BCA0–1BCA3, U+1D173–1D17A
  - U+E0001 and U+E0020–U+E007F

  The listed controls and bidi and zero-width characters are escaped correctly (U+061C, U+200B–200F,
  U+202A–202E, U+2066–2069, U+FEFF, C0, C1, DEL), and the output is otherwise reversible.

  Separately, the spelling differs from the help wording: LF and CR print as `\n` and `\r`, and other escapes
  use minimal lowercase hex (`\u{1b}`), not `\u{XXXX}`. This is unambiguous because backslash is doubled, but
  undocumented.
- **Why it matters**:
  - The value shown is not the value stored. Tag characters and soft hyphens are invisible in a terminal, so
    a revealed password or note can carry hidden text that a user or script copies along.
  - The help text promises otherwise.
  - Titles, tags and field names go through the same list, so the same characters reach `list` and `get` raw
    there too. No contract covers those, and the ledger checks for C0/C1/bidi in them pass.
- **Reproduction**: `cargo build -p vault-cli && bash qa/spec-checks/cli/run_all.sh`. Look at the check
  "get --reveal escaping per 'vault get --help'"; its `RAW` line lists the code points. A minimal equivalent of
  the same steps, from the repository root:

  ```sh
  export VAULT_FILE=qa/spec-checks/tmp/r.vault MPW='tidy-Walrus-orbit-Velvet-42' VAULT_DEV_KDF=1
  target/debug/vault --password-env MPW init --kdf-test-params
  target/debug/vault --password-env MPW add --title R
  target/debug/vault --password-env MPW edit R --add password:p
  export S="$(printf 'ab\xc2\xadcd\xf3\xa0\x81\x81')"      # U+00AD, U+E0041
  target/debug/vault --password-env MPW edit R --set-env p=S
  target/debug/vault --password-env MPW get R --reveal | od -c # c2 ad and f3 a0 81 81 appear raw
  rm -rf "$VAULT_FILE"
  ```

- **Suggested fix**: decide escaping by general category (Cc, Cf, plus Zl/Zp and unassigned or private-use
  code points if wanted) instead of a fixed list. Use a small generated table or a crate such as
  `unicode-general-category`, listed per CLAUDE.md. Then update the help sentence to describe the actual
  spelling (`\n`, `\r`, lowercase minimal hex). Add the ledger's Cf sweep, or a unit test over the same set,
  to `vault-cli`.

### L2: spec 04 does not list the `block2` dependency of vault-macos

- **Severity**: low (documentation drift; CLAUDE.md requires new dependencies to be listed)
- **Crate and location**: vault-macos. `crates/vault-macos/Cargo.toml` declares `block2`, used at
  `crates/vault-macos/src/panel.rs:103` (`use block2::RcBlock`) for `beginWithCompletionHandler`. The spec
  line is the "Dependencies:" paragraph at the top of `specs/04-macos.md`.
- **Expected**: 04: "Dependencies: `vault-core` (path), `thiserror` …, and on macOS only `objc2`,
  `objc2-foundation`, `objc2-app-kit`, … `libc`, `zeroize` (QR scan buffers) … Pin all with `=`". The
  spec's own §3b mentions "`beginWithCompletionHandler` (block2)", but the dependency list does not.
- **Observed**: `cargo tree -p vault-macos -e normal --depth 1` has `block2`; the list does not. The ledger
  check reports "in code, not in spec: block2" (2 of 2 runs).
- **Why it matters**: the dependency list is the reviewed inventory for the only crate allowed `unsafe`, and
  CLAUDE.md's dependency rule depends on it being complete.
- **Reproduction**: `bash qa/spec-checks/cli/run_all.sh 2>&1 | grep -A2 "vault-macos normal dependencies"`
- **Suggested fix**: add `block2` (pinned with `=`, reason: completion handler of the non-modal open panel,
  M-04) to the 04 dependency sentence.
- **Status**: spec corrected on 2026-11-27 (04 line 5 now lists `block2`). The ledger's mirrored list in
  `qa/spec-checks/cli/run_all.sh` was updated to match, and the check passes.

## What held up

Each line describes behaviour on the inputs tried. Passing checks are not proofs.

- **Format 3 (01 §4, §9)**
  - New vaults are v3.
  - The manifest opens with SHA-256 over the raw header bytes, and core header bytes are canonical.
  - Tamper map on the password path: `created_at`, both stamps (changed or removed), header extras
    (text and integer keys), `kdf` extras, slot extras, slot `created_at`, enclave slot removed, slots
    reordered and an appended opaque slot each give `Tampered(Manifest)`. On the key path every one of
    them, KDF edits included, gives `Tampered(Manifest)`.
  - Duplicate header keys, as first or last entry, give `Malformed` on both paths.
  - Relabels to 1 or 2 give `WrongPassword` on both paths, also for an empty vault. Relabels to 4 and
    0xFFFF give `UnsupportedVersion`.
  - Item-record unknown keys written by an independent newer writer open, survive a save and a self-merge,
    and stay bound. Removing, changing, adding or moving one gives `Tampered(Item(first id))`; a stale
    entry digest is caught; manifest-record keys give `Tampered(Manifest)`.
  - A three-element entry in a v2 file gives `Malformed`; malformed v3 entries never open.
  - Record order is content-neutral.
  - No v3 bit flip opened (12,000+ flips on the key path, all header bytes on the password path), and
    every cut of three v3 files was an error without a panic.
  - `upgrade_format` is a no-op on v3 and takes v2 to v3, dropping opaque slots. Hostile KDF parameters in
    a v3 header are `Malformed` before Argon2.
- **Guarantee 6 and 03 §5 restamp.**
  - Over 820 merges in 60 random scripts with a coarse shared clock, every merge followed "equal to ours →
    unchanged; equal to theirs with a greater stamp → verbatim; otherwise max + 1".
  - No merge reused a pair from either side's history with other content.
  - Equal-stamp conflicts converge within 1 ms after one exchange and fully after two, as the 00 roadmap
    states.
- **Header merge guard (L-02)**
  - An unstamped v3 peer header is not adopted over a stamped v2 ours.
  - A merge never lowered the version.
  - Two unstamped headers keep ours.
  - An unstamped ours adopts a peer's password change.
  - A save stamps 1 and our device id.
  - Guarantee 11 holds as worded.
- **Backups (03 §4)**
  - Unvalidated entries (garbage, foreign vault) never satisfy the hourly rule, are never deleted and are
    listed last.
  - Forged-body holders never cost an authentic snapshot.
  - Snapshots under a rotated key are never pruned: 20 of 20 kept, against 4 of 20 in the control.
  - More than 10,000 entries skips retention, and `backup_now` still succeeds.
- **Unsaved fallback (L-05)**
  - The fallback path, name, 0600 file, 0700 folders and `BackupTaken` are as specified, and `vault.bin` is
    untouched.
  - `backups()` returns `UnsafePackageDir` while the entry is planted.
  - After Repair the copy lists as `Unsaved`, restores and deletes.
  - Without a fallback folder the outcome is `Unpreserved`. A symlinked vault-id folder is not written
    through.
  - Foreign, nested, root and outside paths give `NotABackup`.
- **`repair_package`**
  - It is a no-op on a healthy package.
  - It moves a plain file, a symlink (as the link), a FIFO and a dangling link without touching link
    targets.
  - It never reuses an existing name across a 32-second collision range and never touches `vault.bin`.
  - A newer-version stub keeps blocking saves.
- **Quarantine (03 §1.1)**: tested only for restore and the grace period; see Limits.
  - Restore works at unlock, in `attachment_state` and in `open_attachment`.
  - Copy selection takes the lowest copy number with the correct size; wrong-sized copies are never
    restored.
  - A blob already in `attachments/` wins.
  - A symlinked `orphaned/` moves nothing.
  - A fresh orphan stays.
- **Freshness (03 §8)**
  - `Freshness::of` matches an independent computation on fresh files and every fixture tried, tombstones
    included.
  - `on_disk_freshness` tracks create, save, a fresh locked handle, `PrimaryMissing` (None) and recreate.
  - The `Merged` event's `peer` describes the external file.
  - A stale authentic primary merges nothing and our newer state is written back.
  - Code read: the app raises its anchor only from authenticated or self-written files. A `KeyMismatch`
    file replaces `locked` unverified, but no anchor raise happens on that path.
- **Importer caps (02)**
  - CSV: 100,000 rows import and 100,001 give `TooLarge`; a 65 MiB value and 67 MiB over 70,000 rows also
    give `TooLarge`.
  - 1PUX: exactly 10,000 entries import and 10,001 give `TooLarge`; so do a hand-made ZIP64 directory and a
    17 MiB `export.data`. A `export.data` declaring 100 B is an error.
  - 1PUX: 100,000 items import and 100,001 give `TooLarge`.
  - A KDBX4 whose XML inflates past 256 MiB gives `TooLarge("KeePass database content exceeds 256 MiB when
    decompressed")` in about 1 s.
- **KDF floor and TOTP**
  - `below_recommended` is correct at every edge tried, and `validate` does not enforce the floor.
  - The CLI refuses `init --kdf-test-params` unless `VAULT_DEV_KDF=1` (unset, 0, true, yes and 2 were all
    refused) and hides it from help.
  - A below-floor vault prints exactly one stderr line per command; a calibrated vault prints none.
  - TOTP periods 0, 301, 2^32, negative, fractional and empty are `InvalidUri`; a repeated parameter cannot
    smuggle a large period (last value wins, still capped).
  - The CLI refuses periods 0, 301 and 999,999 at `add`, and the period-300 code matches an independent
    HMAC.
- **Format 3 through sync**
  - A merge that takes peer records with unknown keys leaves a file that opens on both paths and passes the
    spec binding.
  - A v2 per-file copy is absorbed and the primary stays v3.
  - A header-tampered v3 sibling is not merged and not deleted (`Error("… tampered with: Manifest")`).
  - An older authentic v2 primary under an unlocked device is written back as v3.
  - A v3 primary relabelled 2 gives `KeyMismatch`, and saves are refused without data loss.
- **Security read (code)**
  - `forbid(unsafe_code)` holds in core and sync; no `unsafe` in the CLI or app sources searched.
  - The only secret-dependent checks are AEAD tags. The `==` comparisons on secrets are on item values
    (merge dedup, confirm fields), not key checks.
  - The NFC password buffer and KEK are `Zeroizing`, and `PlaintextExport` wipes on drop.
  - TOTP errors carry fixed text only; CSV errors are the `csv` crate's position messages; decode errors
    name field and type, never values.
  - Sync errors carry the user's own vault paths only.
  - Backup header reads are capped at 16 KiB and authentication at 512 MiB per pass. Files are re-stamped
    after authentication.
  - `delete_backup` resolves only the parent and re-lists before removing.
  - CLI export uses exclusive 0600 creation, fsync, and removal of partial files.
- **Code read only**
  - The vault-macos non-modal panel matches 04 §3b: it returns at once; the handler runs once on the main
    thread, frees the slot before `done`, and is ignored off-main; `cancel_open_panel` is main-thread only
    with a SAFETY comment.
  - The vault-app idle lock matches 05 §Auto-lock: the larger of the monotonic and wall deltas, a wall
    clock moved back counting as zero, a post-sleep gate on keys and mouse with ⌘L/⌘Q passing, and the
    clipboard deadline judged the same way.

## Notes

These are spec ambiguities or drifts, not counted as bugs.

- **N1. `created_at` carry**: 02 guarantee 6 says a carry "now restamps and reports `updated`", and the code
  does that (stamp 100 → 101, `updated: 1`). 01 §4 still says "a differing created_at alone is not a change
  and never bumps modified_at". One of the two sentences should go.
- **N2. CLI upgrade to format 3**: 01 §9 says "the app and CLI upgrade on the next password unlock". The
  README says the CLI does it "with `vault upgrade`". The CLI does the latter: `vault list` on a v2 file
  leaves it at version 2 and prints "upgrade available (to 3): run `vault upgrade`".
- **N3. Fallback path refusal kind**: 03 §4 says a fallback path outside the allowed parents is
  `NotABackup`. When `<fallback>/<vault_id>` is itself a symlink, `delete_backup` returns
  `UnsafePackageDir` instead (by design per the `backup_home` docs in `crates/vault-sync/src/synced.rs`).
  Nothing is deleted.
- **N4. Header read cap**: 03 §4 says the header check reads "at most 256 KiB". The code caps it at 16 KiB
  (`crates/vault-sync/src/backup.rs:53`, `MAX_HEADER_LEN`), which is stricter. A header past 16 KiB (over
  about 100 slots) would never validate.
- **N5. "Nothing is deleted this pass"**: 03 §4 says a holder that fails authentication "means nothing is
  deleted this pass". The code skips only the snapshots that holder displaces (`apply_retention`,
  `backup.rs` around line 795). Measured: one forged file 300 days old did not stop the weekly tier from
  pruning (2 of 12 kept).
- **N6. Forged-body copies stop pruning**: forged-body copies placed in the same buckets as authentic
  snapshots stop pruning there indefinitely (12 of 12 kept, against 2 of 12 in the control). The forged
  files are never removed either. This is consistent with the spec sentence, but the resulting growth
  (hourly snapshots kept in those buckets) is not listed among the residuals.
- **N7. Third-device pair collisions**: guarantee 6 covers "the peer's record … or our own pre-merge
  record". In 3-device scripts, about 30 of 820 merges produced a record at an (id, stamp) pair that a third
  device had independently used with other content. Someone holding that device's file could splice its
  record in until the next exchange. This is the same residual class as two same-millisecond local edits
  (where the spec's "equal to ours → unchanged" branch also keeps a shared pair for one exchange).
- **N8. Planted `backups` file and saves**: 03 §4 says that while `backups` is planted, "saves that need a
  snapshot … refuse with it". `vault add` with a planted plain file instead writes `vault.bin`, exits 0 and
  prints `warning: backup failed: …/backups is a symlink or not a directory; refusing to use it`. That fits
  05 §2.3's `BackupFailed` wording and the 00 "only a failed save makes [the exit code] non-zero" rule. The
  03 sentence can be read either way.
- **N9. Wrong length in an error message**: `as_key` (`crates/vault-core/src/format.rs:463-466`) calls
  `zeroize()` on the byte vector before formatting `got {}`. `Vec::zeroize` also clears the vector, so the
  message reports length 0 whatever the real length. Cosmetic; code read only, not reproduced.
- **N10. Peer record unknown keys dropped**: for an id on both sides, a merge keeps ours' record-level
  unknown keys and drops the peer's, even when the peer's record is adopted verbatim (documented in
  `merge.rs`, "Extras"). Observed: a newer writer's `zz_shared` key on a shared item was dropped, while a
  peer-only item kept its key, and the file still opens. 01 §9's "writers preserve unknown keys they read" is
  not met for that case. Nothing writes record-level keys today.
- **N11. Stale ledger lines**: the format-3 commit updated the Rust ledger files for version 3, but two lines
  in `qa/spec-checks/cli/run_all.sh` still expected version 2 after `vault upgrade` and treated a version-3
  per-file copy as "newer". Both now use 3 and 4, keeping their intent.

## Limits

- **Tooling interruption**: Bash failed with an adapter error ("no active turn") during step 4. The
  remaining step 4 items were done by reading code. The planned CLI probe of rejected-TOTP error text was not
  run; the conclusion that errors carry no secret comes from `crates/vault-core/src/totp.rs:11-19` and
  `:85-162`.
- **Quarantine by age**: moving an orphan into quarantine after 24 hours, and expiry after 30 days, could
  not be triggered. Both are measured from `max(mtime, ctime)` and ctime cannot be set back from a test.
  Only restore and the not-before-grace side were checked.
- **Code read only**: vault-macos (panel, idle sources) and vault-app (freshness anchor, idle lock, stale
  toasts) could not be driven. Touch ID and signing remain unverified on hardware.
- **Not run**: no fuzzing, no `cargo deny` or `cargo audit` (no `Cargo.toml` change in this run), no
  mutation testing.
- **Environment**: one Mac, local APFS, no real iCloud, Dropbox or NAS. Watcher timing assumptions (500 ms
  debounce) held on this machine only.
- **Coverage**: the random merge scripts used 60 seeds of 40 steps. The bit-flip sweeps covered one fresh
  file plus fixtures. Passing checks show behaviour on those inputs only.
