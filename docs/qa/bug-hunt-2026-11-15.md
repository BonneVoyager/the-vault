## What held up

These checks passed on the inputs listed. They show the behaviour on those inputs; they are not proofs.

**Field order, 03 §5 (`tests/field_order.rs`):**
- **Winner's order, then the loser's extras.** The loser holds `[x1, h, f, x2, g]` at t=2000. The winner adds `y` at t=3000 and holds `[f, g, h, y]`. Both sides end with `[f, g, h, y, x1, x2]` after one exchange and are fully equal after two (`fo01`).
- **A reorder alone** restamps the item (`modified_at ≥ now`) but leaves every field stamp at its old value. A peer's value edit at t=2000 therefore survives a reorder at t=3000, and the reorder wins the order (`fo02`).
- **A later edit elsewhere wins the order**, as the spec accepts: a reorder at 2000 is lost to a value edit at 3000 (`fo03`).
- **Ties:**
  - At the same millisecond, the greater `device_id` supplies the order on both sides. This was repeated eight times with random ids (`fo04`).
  - With a cloned device id at the same millisecond, the orders are equal after one exchange and the items fully equal after two (`fo05`).
- **Three devices** made a reorder plus an add, an add, and a reorder plus a removal, then pulled in a fixed order and ran three rounds. They converge. The removed field stays removed, nothing is duplicated, and the winner's relative order holds (`fo06`).
- **Delete:** a reorder after a delete resurrects the item with that order. A reorder before the delete leaves the item deleted (`fo07`).
- **Markers:** the winner's removal marker filters the loser's reordered copy of that field, and the loser's new field is appended (`fo08`).
- **Merge laws with reorders:** 120 seeded scripts with 2 or 3 devices, 50 steps each, using shuffles, single moves, inserts at a position, removals, title changes and deletes, with clock ties. All laws held, in debug and release (`fo09`):
  - Content equal within 1 ms after one exchange.
  - Fully equal after two exchanges.
  - Merging the same file twice is a no-op.
  - N devices are equal after N rounds, and an extra round changes nothing.
- **vault-sync:**
  - A's reorder survives B's pre-write merge. It is on disk and in B's memory, and A's watcher brings B's item in (`fo10`).
  - A newer reorder in an in-package `vault 2.bin` and in a sibling `fo 2.vault/` is adopted by `vault sync`, and both copies move into `backups/` (`fo11`).

**Concurrent CLI edits, 03 §5:**
- **Same attribute:** six parallel `edit --tag tN` calls all exit 0. The base tag is kept, exactly one `tN` survived in every run, and no foreign tag appears (`fo12`, and `run_all.sh`).
- **Different attributes and fields:** six or seven parallel `edit` processes on one item, changing title, favorite, a tag, the icon, the username, the url and the password via `--set-env`. Every change survives and no process echoes the secret. This ran in four Rust repetitions plus three shell repetitions (`fo13`, and `run_all.sh`).

**vault-macos host facts and login launch (`tests/host_facts.rs`, driven as a library):**
- `os_version()` equals the `sw_vers` value, with the patch omitted when it is 0 (`hf01`).
- `model_identifier()` equals `sysctl -n hw.model`. It is printable ASCII and under 256 bytes (`hf02`).
- Neither string contains the host name, the short host name or the user name (`hf03`).
- `launched_as_login_item()` is false on a test thread and on a spawned thread (`hf04`).
- 32 threads × 50 calls return the same values, with no panic (`hf05`).

- No removed ⌘1/⌘2 pane-focus key is described.

## Notes (spec ambiguities, not counted)

**Diagnostics slot lines while locked.** 05 §2.5 says header-derived lines read "locked" while locked. `diagnostics_text` does that for the format version, KDF, items and trashed lines. It prints "Touch ID slot" and "passkey slot" as yes/no from `locked_summary()` instead (`state/diagnostics.rs:71-78`, `156-160`).

The only caller is the Settings ▸ Security button. Settings opens only when `main_active()` holds (unlocked main screen, `state/session.rs:98`), and locking closes the sheet. The locked branch is therefore not reachable from the UI, and the slot list is plaintext header data in any case. If the function ever gets a second caller, either print "locked" for these two lines or let the spec say that slot presence is shown while locked.

**License keys are audited as passwords.** The License template stores the key as a `password` field (05 §2.3, so it is masked, copied and revealed like a password). The per-field audit covers every `password` field, so the following happen:

- A short key gets "Weak Password — This password is easy to guess and should be changed."
- A key shared by two License items, such as a family or volume license, gets "Reused Password — Used by 1 other item. Reuse lets one leak unlock several accounts."
- The list shows the red "!" badge on that item.

This follows the spec's literal text. The owner may want to exempt License keys, or more generally fields under a `#license` item, from the reuse and weak checks. The case was not provoked in the app.

**The CLI has no Server or License template.** `vault add --template` accepts only `login`, `note`, `card` and `identity`. 05 §2.3 specifies the templates for the app's ⌘N menu, and 00's phase-1 CLI list does not mention templates. This is not a deviation, but the sync lab cannot create those item shapes from the CLI.

**The 2026-11-08 Notes are resolved by the spec text.**
- 03 §5 now specifies field order (winner's order, then the loser's extras) and the rule for concurrent CLI edits. `fo01`–`fo09` and `fo12`/`fo13` match it.
- In every concurrent `--tag` run, exactly one of six tags survived and every process reported success. This is the documented "greater stamp wins" behaviour.

**The Help page's shortcut table is a subset.** `docs/help.md` lists 14 rows. It omits ⌘? (Help itself), ⌘⇧Z (Recover), ⌘M and the hold-⌥ reveal, although the reveal is described in the prose. Nothing listed is wrong. The page also says to "drag the handle on the left of a field". The editor rows draw a `GripVertical` glyph and the drag preview shows it, which matches.
