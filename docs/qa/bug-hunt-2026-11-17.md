## Summary

The run found two low-severity bugs and no high or medium ones.

1. **L1: the test hook can raise the save-lock wait.** 03 §2 says the hook "can only lower it". A first call with 15 s or 60 s makes the wait 15 s or 60 s. Production is not affected, because the hook is compiled only with `test-support` or `cfg(test)`.
2. **L2: a flaky vault-core unit test.** `debug_redacts_secrets` fails about 1.8 % of runs, because random UUIDs in the Debug output can contain the digit runs it forbids. It failed once in the repository's `cargo test --workspace` in this run. It predates the wave.

**Security read of the lock hook (priority 1).** The hook cannot shorten the wait in production:

- The static, the function and the re-export are all gated. The non-test `lock_timeout()` returns the 10 s constant.
- The normal-edge feature graphs of vault-app and vault-cli do not enable `test-support` (`lh08`).
- The production CLI waited the full 10 s against a held lock, even with override-looking environment variables set (`lh07` and `run_all.sh`).
- `SaveLockTimeout`'s message carries no path and no secret.

**Icons (priority 2).** Item and field icons with any strings round-trip, merge and converge. The checks covered the legacy kind "logo", odd identifiers, non-palette and malformed colours, and a 65 MiB value, which hits the save cap cleanly. Every fixture opens. The CLI stores `symbol:<name>` verbatim and sanitises control bytes on output. By code read, the app resolves icons only through an exact identifier map, so no stored string can reach an asset path.

**Editor (priority 3).** This was a code read plus two probe tests in a scratch copy:

- The cache of per-field strength scores and notices is invalidated on value, item, vault and kind changes.
- The flash timer is generation-checked, keyboard moves do not flash, and Tab reaches ↑, ↓ and the trash.

**Notes.** Nine items are recorded under Notes and not counted. They include history placement for a second password field, a CLI colour dropped by the picker, and the kebab-case identifier mismatch between the CLI and the app.

## Findings

### L1: `shorten_lock_timeout_for_tests` raises the lock wait above 10 s on a first longer call

- **Severity:** low
- **Crate and file:** vault-sync, `crates/vault-sync/src/lock.rs:41`, `:56-60`, `:65-69`
- **Expected:** 03 §2: "The lock wait is 10 s (`SaveLockTimeout`, nothing written); test builds may shorten it process-wide through the hidden, `test-support`-gated `shorten_lock_timeout_for_tests`, which **can only lower it**, and production code has no override." The function's own doc says "can only go down".
- **Observed:**
  - The override starts at `u64::MAX` ("none") and the hook stores `fetch_min(ms)`. `timeout_with_override` returns `Duration::from_millis(override_ms)` for any value other than `u64::MAX`, without comparing it with `LOCK_TIMEOUT`.
  - A first call with 15 s made a save against a held `.lock` wait 15 002 ms. A first call with 60 s made it wait 60 001 ms. Both ended in `SaveLockTimeout`, with nothing written.
  - A later longer call after a shorter one is correctly ignored (`lh04`).
  - The crate's unit test does not catch this. It calls 100 ms first and only then 60 s.
- **Why it matters:**
  - The hook breaks its specified contract.
  - In a shared test binary, one test that passes a "generous" value lengthens every lock wait in the process past production's 10 s. Tests then hang, or mask timing bugs.
  - Production is not affected: the code is compiled only with `cfg(test)` or `test-support`.
- **Reproduction:**
  ```sh
  cargo build -p vault-cli
  cd qa/spec-checks && cargo build --bins
  cargo test --test lock_hook lh03          # fails: "raised past 10 s: elapsed_ms=60001 ..."
  d=$(mktemp -d tmp/lh-XXXX); ./target/debug/lock_hook "$d" 15000; rm -rf "$d"   # elapsed_ms=15002
  ```
- **Suggested fix:** Clamp at the source, for example `let ms = ms.min(LOCK_TIMEOUT.as_millis() as u64)` before `fetch_min`, or return `min(LOCK_TIMEOUT, override)` in `timeout_with_override`. Add a unit case that calls the hook with a value above 10 s first, and run it in its own process (or assert on `timeout_with_override(60_000)`).

### L2: Flaky `vault-core` unit test `item::tests::debug_redacts_secrets`

- **Severity:** low (project test reliability; the product is not affected)
- **Crate and file:** vault-core, `crates/vault-core/src/item.rs:734-786` (assertions at `:782` and `:784`). The test dates from `52850a9`, before this wave.
- **Expected:** The four pre-commit checks in CLAUDE.md, and 02's "write tests for each" guarantee, assume a deterministic suite. Debug redaction itself is correct: no key or nonce bytes are printed.
- **Observed:**
  - The test asserts that the Debug text contains neither `"167"` (key byte 0xA7) nor `"184"` (nonce byte 0xB8).
  - That text also contains random v4 UUIDs: the item id from `Item::new`, and the field id from `Field::new`, which `Field`'s Debug prints at `item.rs:213` and the history entry repeats.
  - The hex form of a UUID contains "167" or "184" in about 1.5–2 % of draws.
  - Measured: 18 failures in 1000 runs of the test binary. One failure occurred in this run's repository `cargo test --workspace`, with "key byte 0xA7 = 167 must not appear". Forty `cargo test` reruns then passed.
- **Why it matters:** The suite fails intermittently on unchanged code, which teaches people to rerun red runs. Once CI exists (00 roadmap item 1), it will flake there too.
- **Reproduction:**
  ```sh
  cargo test -p vault-core --lib debug_redacts_secrets --no-run
  B=$(ls -t target/debug/deps/vault_core-* | grep -v '\.d$' | head -1)
  f=0; for i in $(seq 1 1000); do $B --exact item::tests::debug_redacts_secrets -q >/dev/null 2>&1 || f=$((f+1)); done; echo $f
  ```
- **Suggested fix:**
  - Give the item and field fixed ids (for example set `item.id = Uuid::nil()` and `fields[0].id = Uuid::from_u128(1)`).
  - Alternatively, assert on the byte-list shape that a leak would print: `"167, 167"`, `"0xa7"` and `"[167"`, rather than on a bare 3-digit substring.

## What held up

These checks passed on the inputs listed. They show the behaviour on those inputs; they are not proofs.

**03 §2 lock and hook (`tests/lock_hook.rs`, each library case in its own `lock_hook` process):**
- **Default wait:** with no override, a save against a perl-held `flock` waited 10.0 s and returned `SaveLockTimeout` (`lh01`). Nothing was written:
  - the file was byte-identical;
  - no tmp file was left;
  - the vault stayed dirty;
  - the same edit saved once the lock was released;
  - the error text carries neither the master password nor the package path.
- **Lowering:** 1 s gave about 1 s (`lh02`). 1 s then 5 s kept 1 s (`lh04`). Zero is clamped to 1 ms and gave up at once without panic (`lh05`). With 17 concurrent callers the minimum, 700 ms, won (`lh06`).
- **Production CLI:**
  - `target/debug/vault` built by `cargo build -p vault-cli` (no `test-support`) waited 10 s, failed, and wrote nothing.
  - This held with `VAULT_LOCK_TIMEOUT`, `VAULT_LOCK_TIMEOUT_MS`, `VAULT_SAVE_LOCK_TIMEOUT(_MS)`, `VAULT_TEST_LOCK_TIMEOUT_MS` and `LOCK_TIMEOUT_MS` set to tiny values. Two packages ran in parallel (`lh07`), and the shell repeated it (`run_all.sh`).
  - The add succeeded once the lock was released.
- **Shipping feature graph:** `cargo tree -e normal,build,features -i vault-sync` for vault-app and for vault-cli shows no `test-support` (`lh08`). `package.sh` builds `--profile dist -p vault-app`, which resolves the same way.
- **Code read:**
  - The static, `shorten_lock_timeout_for_tests`, `timeout_with_override` and the test `lock_timeout()` are all `#[cfg(any(test, feature = "test-support"))]`. The re-export in `lib.rs` is `#[cfg(feature = "test-support")] #[doc(hidden)]`. The non-test `lock_timeout()` returns `LOCK_TIMEOUT`.
  - The only non-vault-sync caller is a vault-app test inside `mod tests` (`state/sync.rs:1123`).
  - `SaveLockTimeout` displays "another process is writing this vault".

**Icons (`tests/icon_catalog.rs`):**
- **Core round trip:** item icons with every combination of these round-trip exactly through serialize, parse and unlock, as canonical CBOR, identical under the independent decoder (`ic01`):
  - kinds: symbol, logo, letter, image, "" and a future kind;
  - 17 identifiers: kebab and Pascal Lucide names, " ", NUL, ESC/BEL, CR/LF, `../../../etc/passwd`, RTL override, emoji, a combining mark, and 256 KiB;
  - colours: none, `#123456`, `#abcdef`, `#FFF`, `red`, "", `#GGGGGG`, `javascript:alert(1)`, and 10 000 `#`.
- **Item icon merge:**
  - Three devices: a newer odd symbol with a non-palette colour beats an older logo. It survives a title edit on a third device, all three converge, and the merge is idempotent (`ic02`).
  - Cloned-device ties at the same millisecond converge within two rounds for four pairs of odd icons (`ic03`).
- **Legacy "logo" (`v1-icon.vault`):**
  - Its logo survives a title edit, serialization and merges in both directions. A peer's later symbol replaces it on both sides.
  - The file stays at its version (`ic04`).
- **Field icons:** the same identifier set round-trips, with "" read as none. An icon-only change on one device and a value change of another field on the other both survive and converge (`ic05`).
- **Save cap:** a 65 MiB item icon is refused with `VaultTooLarge`. The file is unchanged, the vault stays dirty, and no tmp file is left. The save succeeds after the icon is replaced (`ic06`).
- **Fixtures:** every committed `.vault` fixture parses, unlocks, re-serialises at its own version and re-opens to equal items (`ic07`).
- **CLI `--icon symbol:<name>[:#RRGGBB]`:**
  - It stores `a-arrow-down`, `AArrowDown` with `#abcdef`, `Star` with `#ABCDEF`, `NotInCatalog`, `../../x`, an ESC/BEL string, an emoji and a 100 000-character name verbatim.
  - `get` and `list` print no raw control bytes.
  - `symbol:`, a 5-digit colour, `red`, `logo:…`, `image:…` and "" are refused and leave the icon alone. `auto` clears it (`ic08`, `run_all.sh`).
  - Six concurrent `--icon` edits all succeed, and one survives (03 §5 "same attribute").
- **Hostile icons from a peer file:**
  - The icons were: logo with an OSC title escape and a `javascript:` colour, a symbol with NUL, an image with a non-UUID value, empty kind, and a future kind with a path value.
  - `list`, `get`, `get --reveal`, `export`, `edit --tag` and `sync` all handled them. `sync` absorbed both conflict-copy shapes (in-package `vault 2.bin` and sibling `hi 2.vault/`).
  - Every command exits 0 and prints no raw control bytes. The CSV carries no icon. An edit of another attribute keeps every icon, and the newer peer icon is adopted from both copy shapes (`ic09`).
- **CLI on `v1-icon.vault`:** `list` and `get` work. A title edit and `upgrade` keep every icon, and `--icon auto` clears the logo (`ic10`).

**vault-app (code read only, plus two probe tests in a scratch copy that was then deleted):**
- **Icon resolution (`icon.rs`):**
  - `symbol(name)` is an exact lookup in a map of `IconName` identifiers. No stored string is ever turned into an asset path, so `../…` or a 64 MiB value cannot reach the asset source.
  - Unknown symbol → the letter avatar. `logo` → the automatic icon. A non-UUID `image` → the automatic icon. Unknown kind → `Unsupported`, drawn as the letter, with the stored value untouched.
  - `color_override` accepts only the 8 palette colours, so any other `#RRGGBB`, or garbage, renders with the item's palette colour, as 05 says.
  - Field icons resolve through the same `symbol()` in read mode, in the editor button and in the drag ghost. An unknown name draws no icon, or the placeholder in edit mode.
- **Icon search:**
  - Results are computed in `PickerSearch::set_query`, only when the query changes. The cap is 120.
  - Curated symbols come first in their order. Catalog icons follow, prefix matches first, then alphabetically. Curated icons are excluded from the catalog group, so nothing is listed twice.
  - The generated `IconName::path()` has 1830 unique paths, so there are no aliases.
  - The scroll offset is reset on every `InputEvent::Change`. The query is cleared when either picker opens or closes, when an edit starts or ends, and is never persisted.
- **Cached notices (`editor.rs` `IssueCache`):**
  - Entries are recomputed when the row's value changes, which includes undo through the input.
  - All entries are cleared when the item changes or the listing's audit `Rc` changes. `vault_changed` replaces that `Rc` on every vault change, merges included.
  - Rows that are no longer `password` are dropped. PIN rows are never scored, and a kind change back to password rescores.
  - The cache is cleared at the start and end of each edit session. Cached values are `SecretString`s, zeroized on drop.
- **Move flash:**
  - Each flash gets a new generation. The fade animation is keyed by it, and the end timer clears only its own generation.
  - A second move restarts the flash. Keyboard moves (`ClickEvent::Keyboard`) do not flash. Under Reduce Motion the fill is solid for 300 ms.
  - The flash is cleared at the start and end of each session.
- **Arrows and Tab:**
  - The hidden ↑/↓ keep their space and Tab stops (focus-handle slots).
  - Probe: from row 2's value input, Tab visits ↑, ↓ and then the trash. The trash is reachable.
- **Drag:** the dragged row's ghost carries the name, kind and icon only, never the value. Hover is suppressed during a drag.

**Unsafe, secrets, logging:**
- `vault-core` and `vault-sync` keep `#![forbid(unsafe_code)]`. vault-app and vault-cli contain no `unsafe`.
- The wave's only new output is a `println!` of timings in the perf test.

**Standing areas (the regression ledger, unchanged and passing):** file format and tamper detection, keys and slots, merge rules and laws, field order, sync with two handles, conflict copies of both shapes, backups and retention, attachments, CLI end to end with concurrent writers, cut-at-every-offset and bit-flip sweeps, hostile KDF parameters and KDBX headers, and the generator and TOTP checked against independent computations.

## Notes (spec ambiguities and observations, not counted)

1. **History of a second password field sits under the first password row.**
   - `detail::history_row` (`detail.rs:1003`) places an entry under its own field only when that field is a PIN. Every other entry goes under the first password row.
   - A probe confirmed it: with two password fields, an entry whose `field_id` is the second field returns row 0. As a result, "Clear history" on that disclosure also clears the second field's entries.
   - 05 §2.3 says "History entries sit under the row of the field they belong to". The sentence is inside the `pin` bullet, and the code comment says "as before PINs". The owner should say whether this applies to passwords too.
2. **The picker drops a CLI-set colour that is not in the palette.**
   - Opening and saving the editor keeps the icon as stored.
   - Picking any symbol or "Automatic" rebuilds the icon from `color_override`, which ignores colours outside the palette (`icon.rs:435`, `:450`). A stored `#123456` is therefore replaced by no colour.
   - This is consistent with "renders with the item's palette colour", but the CLI's choice is lost silently.
3. **The CLI and the app disagree on symbol spelling.**
   - `vault edit --icon symbol:key-round` (Lucide's own kebab name) is accepted and stored. The app only knows `IconName` identifiers (`KeyRound`), so the item shows a letter avatar without any warning.
   - The CLI help says `<IconName>`, while 05 says "<Lucide identifier>". A CLI warning for names outside the catalog, or one spec sentence fixing the spelling, would close the gap.
4. **Icon search matches more than names.**
   - Curated symbols also match on their label and their PascalCase identifier (`icon.rs:152`). For example, "bank" finds Landmark, and "keyround" finds KeyRound but no catalog icon spelled that way.
   - 05 describes matching on the kebab-case name only. The result is a benign superset.
   - A query made only of hyphens (`-`) becomes a space and lists the first 120 multi-word names.
5. **Development binaries can contain the override.**
   - After `cargo test --workspace`, `target/debug/vault` is relinked with vault-sync `test-support` through Cargo feature unification: `nm` shows `LOCK_TIMEOUT_OVERRIDE_MS`.
   - `cargo build -p vault-cli`, `cargo build --workspace` and the dist build do not include it.
   - No non-test code calls the hook, so even such a binary waits 10 s. "Production code has no override" holds: by feature gating in shipping builds, and because no production code calls the hook in development binaries.
6. **The 200 ms override applies to the whole vault-app test binary.** `busy_save_toasts_and_autosave_retries_once` (`state/sync.rs:1123`) shortens the wait for every later test in that process. No app test that legitimately waits for a lock was found. A future one would time out after 200 ms on a loaded machine, not 10 s. L1's fix does not change this.
7. **The About tab shows no licenses.**
   - 05 §2.5 says "About: version, licenses". The tab shows only the version.
   - This wave embeds the whole Lucide catalog (ISC license, which asks for its notice to be kept with copies) and deleted the brand pack's license file.
   - The gap predates the wave.
8. **The ledger was edited by the builders.**
   - `d698738` changed `qa/spec-checks/tests/field_order.rs` `fo13` to address the item by id instead of by title, and added a dev profile to the QA crate's `Cargo.toml`.
   - The change was reviewed. The title job renames the item while the other jobs look it up by title, so the old check raced with itself. The new form asserts the same survivals. The C2 block in `run_all.sh` already used the id.
9. **Another process changed the working tree during the run** (see the introduction). The authoritative project-suite numbers come from the clean `HEAD` copy.
