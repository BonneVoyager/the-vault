# Bug hunt 2026-10-31

Independent, spec-derived run after the field-id wave (format version 2). The checks were written from `specs/00`–`05` and `README.md` before reading the source, the project's tests or `PROGRESS.md`. They live in `qa/spec-checks/`, a standalone crate, with black-box CLI checks in `qa/spec-checks/cli/run_all.sh`.

## Summary

One high-severity finding can lock a user out of their vault. When one device upgrades a version 1 file to version 2 while another device still holds it, the second device writes a file that no password opens. This happens in the normal two-Mac flow, because the app upgrades automatically on a password unlock. It also happens with the CLI alone: `vault upgrade` racing a `vault add` broke the vault in 8 of 8 runs.

One medium finding breaks merge convergence. Same-millisecond edits of one field can leave two devices showing different values forever.

Two low findings remain:

- More than 64 field removals in one item resurrect the oldest removed fields on merge.
- Spec 01 still has two stale lines.

All three code findings from 2026-10-30 are fixed: vault `created_at`, the `SaveBlocked` event, and the key-rotation event. The project's own suite is green.

**Update, same day:** H1, M1 and L1 were fixed in vault-core, with spec amendments in 01 §9 and 03 §5. On a rerun every check passes. That includes the H1, M1 and L1 reproductions, and four checks ported to the amended rules, which are listed under Notes. L2 was not rechecked.

## Findings

### H1. Merging across the version 1 / version 2 boundary writes a vault that no password opens

- **Severity:** high
- **Where:** vault-core, `crates/vault-core/src/vault/merge.rs:139-151`. When the other side's header stamp is newer, `merge_from` adopts its `slots`, `kdf`, stamp and device id, but not `header.format_version`. The upgrade itself is correct (`crates/vault-core/src/vault.rs:989-1011`). The app triggers it on every password unlock of a version 1 file (`crates/vault-app/src/state.rs:804`, `:1140`), and `vault upgrade` triggers it in the CLI.
- **Expected:**
  - 01 §2 says the slot "AAD for unwrapping any slot: `magic || format_version || vault_id || slot.id || slot.kind`".
  - 01 §9 says "A save never changes a file's version, because every slot AAD binds the version", and `upgrade_format` "moves a file to version 2 by re-wrapping the password slots".
  - 03 §5 says a slot change on one device "survives the other device's next save".
- **Observed:** the newer header's slots carry the other version's AAD, and the merged vault keeps its own version. Both directions fail. In each case the cached key still opens the file, so the damage stays hidden until the next password unlock.
  - **Version 1 holder adopts an upgraded header:** it writes a version 1 file whose slots are wrapped for version 2. The independent decoder confirms that the slot opens only with the version 2 AAD, and `unlock` returns `WrongPassword`.
  - **Version 2 holder adopts a newer version 1 header:** this happens when the other device changes the password after the upgrade. It writes a version 2 file with version 1 slots, and the new password fails.
- **Reproduced through every path tried:**
  - A core merge.
  - Two `SyncedVault` handles, both through the pre-write merge and through the watcher.
  - An absorbed conflict copy of both shapes: an in-package `vault 2.bin` and a sibling `cc 2.vault/`.
  - `vault upgrade` while an app handle holds the version 1 vault.
  - `vault upgrade` racing six `vault add` processes. All seven processes exited 0, and the result was an unopenable version 1 file in 8 of 8 runs.
- **Why it matters:**
  - **The two-Mac case:** Mac B stays unlocked through Touch ID, and a Touch ID unlock never upgrades. Mac A unlocks with the password and upgrades automatically. Mac B's next autosave then makes the vault unopenable on both Macs at their next password unlock.
  - **The single-machine case:** running the documented `vault upgrade` while the app is open does the same.
  - **Recovery:** older backups still open, but the user sees "wrong password" and has no hint to restore a backup.
- **Reproduction:**
  ```sh
  cargo build -p vault-cli
  cd qa/spec-checks
  cargo test --test upgrade        # u05 (core, both directions), u06/u07 (sync), u08 (diagnosis), u09 (conflict copies)
  cargo test --test cli_bridge b04 # vault upgrade while an app handle holds v1
  cargo test --test cli_bridge b09 # vault upgrade racing vault add
  ```
- **Suggested fix:**
  - Treat `format_version` as part of the slot unit. Copy it whenever the slots are adopted.
  - Order header precedence by `(format_version, slots_modified_at, slots_device_id)`, so that an upgrade always wins and is never undone. A version 1 password change made after another device's upgrade then loses to the upgrade, and the old password keeps working. Note this in 03 §5.
  - Add the checks above to the project's suite. Add a vault-sync test that saves from a handle opened before the upgrade.

### M1. A same-millisecond field edit can leave devices permanently disagreeing

- **Severity:** medium
- **Where:** vault-core, `crates/vault-core/src/vault/merge.rs:293-297`. The tie-break is `Ordering::Equal => ours.device_id >= theirs.device_id`, which uses the owning items' `device_id`. That id follows the metadata winner, not the field's writer.
- **Expected:** 03 §5 gives the field rule "tie → greater `device_id` of the owning item; tie → ours" and says "Merge is idempotent and commutative, so a ping-pong between two devices converges in one round trip each". It also says "Two devices converge within two merge rounds".
- **Observed:** A and B edit the same field with the same stamp, and B also edits the title later.
  1. A merges B. A keeps its own field, because A's device id bytes are greater. A takes B's metadata, so A's item now carries B's `device_id`.
  2. Both items now carry the same `device_id`. The field tie falls through to "ours" on both sides, and each device keeps its own value.
  3. After four all-pairs rounds in core, A still has "from-A" and B has "from-B". Through vault-sync, after three save rounds per handle, A shows "from-A" while B and the file show "from-B". Each save flips what the file holds.
  4. The seeded random scripts on two and three devices hit the same case at seed 26, which was not commutative and differed after two rounds.
- **Why it matters:** two devices can show different values for one field indefinitely, with no conflict signal. Equal stamps are not only same-millisecond accidents. Two devices whose clocks are behind the field's stamp both write `previous + 1` (03 §5 monotone rule), which produces an exact tie. For non-password fields the losing value is not kept in history.
- **Reproduction:**
  ```sh
  cd qa/spec-checks
  cargo test --test merge_ids mi10   # deterministic, fixed device ids
  cargo test --test sync_edge e10    # through two SyncedVault handles
  cargo test --test merge_ids mi09   # seeded random scripts (seed 26)
  ```
- **Suggested fix:** when field stamps and owning-item device ids are equal, fall back to a total order on field content. One option is the canonical CBOR bytes of the field. Another is to record the writer's device id per field. Update the 03 §5 tie-break row to match. A property test for commutativity over random scripts would cover this (00 testing roadmap item 2).

### L1. More than 64 field removals in one item resurrect the oldest removed fields

- **Severity:** low
- **Where:** vault-core, `crates/vault-core/src/vault/merge.rs:325-333`, `:402-411`, `crates/vault-core/src/vault.rs:57`. `normalize_field_tombstones` truncates markers to `FIELD_TOMBSTONE_CAP`, which is 64, and a field with no surviving marker is taken from the other side.
- **Expected:** 03 §5 says "`removed_fields` markers are unioned (greatest `removed_at` per id, cap 64 newest)". It also says "The former 'field deletion is not tracked' limit is closed".
- **Observed:** one device removes 70 fields of an item while the other device is offline and unchanged. After the merge, 6 removed fields (`f0`–`f5`) are back. In the two-sided version, 40 removals per device bring 16 fields back.
- **Why it matters:** deletions silently undo themselves past the cap. The trigger is rare, such as cleaning up a large imported item, but the user sees removed data reappear. The spec claims the limit is closed.
- **Reproduction:**
  ```sh
  cd qa/spec-checks
  cargo test --test merge_ids mi11 mi05
  ```
- **Suggested fix:** do not drop a marker while its field can still exist on a peer. One way is to purge field markers only with the item-tombstone horizon (`purge_tombstones_older_than`) instead of by count. Otherwise, state the residual limit in 03 §5. The same cap logic applies to `removed_attachments`, where the earlier run accepted it.

### L2. Spec 01 has two stale lines

- **Severity:** low (documentation)
- **Where:** `specs/01-vault-format.md:12` says "`format_version` u16, currently 1". `specs/01-vault-format.md:132` gives the attachment path as `<name>.vault.attachments/<id>.bin`.
- **Expected:** 01 §9 and the README say version 2 is written for new vaults. 03 §1 and 01's own opening line give `<name>.vault/attachments/`.
- **Observed:** new vaults are version 2, and blobs live in `attachments/` inside the package. The README layout section was fixed since the last run, which was the rest of the earlier L4.
- **Why it matters:** §1 is the layout readers implement first, and a reader built from it would reject every new vault.
- **Reproduction:**
  ```sh
  grep -n "currently 1\|vault.attachments/" specs/01-vault-format.md
  ```
- **Suggested fix:** change §1 to "currently 2, see §9" and the §4 path to `<name>.vault/attachments/<id as 32 lowercase hex>.bin`.

## What held up

Each item held on the inputs tried. That shows the behaviour on those inputs, not a proof.

- **Field ids and v1 → v2 derivation (01 §9):** derived ids match an independent SHA-1 UUIDv5 of `"field:" || name || ":" || ordinal`. The inputs covered duplicate names, empty names, a case variant, Unicode names, and an explicit id in the middle of a same-name run. Ordinals count every earlier same-name field.
  - Two password reads and a key read agree.
  - Saving a version 1 file keeps version 1, writes the same ids explicitly, and reopens identically.
  - Duplicate ids are `Malformed`, including an explicit id that collides with a derived one.
  - In version 2, a missing, short, long, text, int, null or 1 MB field id is `Malformed`.
  - Flipping the version bytes in either direction never opens on the password, KEK or key path.
- **Duplicate and empty names (02):**
  - Same-named fields round-trip in order.
  - `Item::field` skips sections, matches ASCII case-insensitively and never matches an empty name.
  - `set_field` by id edits exactly one field, and history carries its `field_id`.
  - Unknown ids give `FieldNotFound`.
- **`update` diff (02):**
  - A rename or kind change keeps the id and bumps the stamp.
  - A removed id gets a marker stamped now.
  - A re-added id is stamped past its marker and the marker is dropped.
  - A duplicate id is rejected and the item restored.
- **`remove_field`:** markers are newest first and capped at 64 locally. The key is omitted while empty and written when non-empty.
- **Id-keyed merge (03 §5), two and three devices:**
  - Same-named fields added on two devices both survive.
  - Rename versus edit resolves whole-field by stamp.
  - Markers win at stamps below and equal to `removed_at` and lose to strictly later edits, with the marker dropped on both sides.
  - A three-device relay never resurrects a removed field, and markers union with the greatest `removed_at`.
  - Sections merge like fields, and history `field_id` survives.
  - Apart from seed 26 (M1), 80 seeded random scripts with add, rename, remove, icon, delete, skew and ties were commutative on content, idempotent, convergent and stable across serialize. They never produced duplicate ids or a field alive under its own marker.
- **`created_at` (01 §4):**
  - `Item::new` sets it, and writers omit it when unknown.
  - Null reads as none, and text, negative, float and bytes values are `Malformed`.
  - Merge keeps the minimum or the known side, never bumps `modified_at`, and reports no change.
  - The CLI's `add` stamps it, and `init` writes version 2.
- **Icons (01 §4, 05 §2.3):**
  - Icons round-trip, unknown inner keys are preserved, null reads as none, and wrong types are `Malformed`.
  - Icons travel with the metadata winner.
  - `vault attach list` and `vault get` hide the image-icon blob, which stays `Present`.
- **Sections (01 §4, 05 §2.3):**
  - `ALL` has 9 kinds, and `Section` is not sensitive.
  - Core stores the value as given, and `set_field` on a section writes no history.
  - Search and CSV export skip the value and the heading.
  - No CLI command (`get` with and without `--reveal` and `--ids`, `list`, `list <query>`, `totp`, `export`) printed or matched a section value.
- **`upgrade_format` (01 §9, 02):**
  - It drops enclave and opaque slots, keeps the vault key, field ids and contents, and stamps the header.
  - It is a no-op on version 2, even with a wrong password, and keeps the enclave slot there.
  - A wrong password gives `WrongPassword` and changes nothing.
  - All five version 1 fixtures upgrade and open.
- **CLI `upgrade`:**
  - A wrong password exits cleanly, leaves the file untouched and is not echoed.
  - It writes version 2 and says Touch ID must be re-enabled. A second run says "already at version 2" and leaves the bytes unchanged.
  - The enclave slot is dropped.
  - `get --ids` prints ids that match the file.
- **Fixtures:** `v2-basic`, `v1-icon` and `v1-meta` carry what 01 §9 lists, and every fixture in the directory opens.
- **Corruption:** every cut offset failed cleanly on `v2-basic`, `v1-meta` and `v1-icon`, plus on the earlier samples. So did 600 bit flips per fixture. Hostile `removed_fields` and history `field_id` shapes gave `Malformed` without panics. 200k markers parsed in under 0.2 s in a release build.
- **Ledger:** every check from 2026-10-30 still passes after the port. That covers format, tamper, keys, header merge, name-addressed merge scripts, sync, both conflict-copy shapes, backups and retention, attachments, TOTP and generator, importers, file modes, and 12 concurrent CLI writers. Last run's L1–L3 now pass (`b01`, `s09b`, `s15b`).
- **Security read:**
  - `upgrade_format` re-wraps with fresh `OsRng` nonces and the version 2 AAD. Its KEK is `Zeroizing`.
  - There is no `unsafe` outside vault-macos: core and sync `forbid` it, and vault-app mentions it only in comments.
  - New error texts name positions and kinds, never values or field names.
  - Field-id derivation runs only after item decryption, so no attacker-sized work happens before the key check.
  - vault-sync blocks saves only for unsupported versions, which is correct; H1 is purely the core header merge.
  - The app runs the upgrade only after a password unlock and removes the Touch ID item. CLI and app parse the icon id the same way (code read only).

## Notes

None of these are counted as bugs.

- **Checks ported after the H1/M1/L1 fixes:** four checks were changed to assert the amended rules. Each still runs as a regression check of the new rule.
  - **`fi07_remove_field_markers_cap_and_order`:** 03 §5 now says "Markers are never dropped by a local removal; a merge caps them at 64 by dropping, oldest first, only markers whose field neither side still holds". The check asserts 80 markers, newest first, after 80 local removals. After a merge where neither side holds the fields, it asserts the 64 newest.
  - **`mi05_removed_fields_union_cap`:** 03 §5 now says devices converge "within two merge rounds, or three when the `removed_fields` cap fires". The check runs three rounds. It asserts that all 80 removals hold and that 64 markers remain, newest first. It also asserts that the decrypted item payloads are byte-equal on both devices and that further pulls report and change nothing.
  - **`u05_merge_across_versions_stays_openable`:** 01 §9 now says the higher `format_version` wins regardless of stamp. A slot change made on the version 1 side after another device's upgrade "is dropped by the merge and must be redone on the upgraded vault". In both merge directions, the check asserts that the merged file is version 2, opens with the old password and refuses the new one.
  - **`u06_sync_upgrade_on_one_handle_survives_other_save`:** the final step had asserted that A's later `favorite` edit and B's earlier title edit both survive. 03 §5 takes metadata (title, favorite, tags) from the item with the greater `modified_at` as one block. So A's later edit wins whole, and A's stale title replaces B's title. The check now asserts that outcome. The new variant `u06b_same_metadata_outcome_without_upgrade` runs the same steps on a version 2 vault with no upgrade and gets the same result, so the loss comes from the metadata rule, not from the upgrade. This is the spec's design. A user can still lose a title edit made on another device when they toggle favorite on a stale copy, which may be worth a per-key metadata merge later.

- **Checks rewritten for the spec change:**
  - `f01` now expects version 2.
  - `f02` accepts the `section` kind and requires a v4 field `id`.
  - `f03` uses version 3 as "> SUPPORTED".
  - `f14` allows a version 1 file to gain exactly an `id` key per field on save, per 01 §9.
  - `s09`, `s09b`, `s10` and `modes` simulate "newer version" with 3.
  - Rebuilt files keep their source version instead of a hard-coded 1. That includes `k03`'s slot AAD, which was a port miss in my check, not a product bug.
  - By-name `set_field` calls became `set_field_named`, and `snap_item` now includes ids, markers, `created_at` and icons.
  - No existing check asserted name-keyed merge, so none had to be inverted. `mi01` asserts the new rule, under which both same-named fields survive.
- **Broken targets:** six targets failed to compile after the wave, not four. `keys` and `sync` also used by-name `set_field`.
- **`set_field_named` on duplicates:** 02 says "first non-Section field matching ...; FieldNotFound / AmbiguousField". The implementation returns `AmbiguousField` when two fields match. Both readings are allowed by the text, so the spec could say which one applies.
- **Marker caps on read:** caps apply on merge, `update` and `remove_field`, not on read. An item with 200k markers loads and re-serializes to about 7 MB. A field present alongside a marker at or past its stamp is kept until the next merge. Only a vault-key holder can write either.
- **Old builds:** the README states that an older build opening a version 1 file still merges by name and can drop a same-named field. That was not tested because no older binary was available.
- **`export --force` symlink:** it no longer writes through a symlink at `--out`, which was a note last run.
- **Icon without `value`:** it is `Malformed`, which is consistent with "core validates types only".

## Limits

- **Platforms not driven:** vault-macos and vault-app were not driven. App behaviour is code read only. Touch ID, Keychain, pasteboard and iCloud were not exercised.
- **API discovery:** public signatures were learned from `pub` lines and `--help` before the checks were written. Implementations were read only in step 4.
- **Watcher timing:** sync checks rely on FSEvents with a 500 ms debounce on one local APFS volume. Real cloud providers, network volumes and eviction were not tested.
- **Randomised checks:** random scripts and bit flips use fixed seeds. Device and item ids are random per run, so which device wins a tie varies, but seed 26 failed in every run. This is not fuzzing.
- **Not tested:** KDBX 3 import (the fixture's password is documented only inside `crates/*/tests`, which this run does not open), passkey slots (not implemented), and the 0.5×–4× retention multipliers.
