## Summary

The run found two low-severity issues and no high or medium ones. Every earlier ledger check passes: 292 Rust checks (including `ra01`, `ra17`, `ra22` and `ra23`, the version-0 and tamper-mapping checks from the last hunt) and 126 CLI checks (including the 04 dependency list, which now names `zeroize`, so last hunt's L4 is closed).

1. **L1: symlinked or FIFO conflict candidates are skipped silently.** A per-file copy (`vault 2.bin`) that is a symlink or a FIFO, and a sibling package (`<name> 2.vault`) that is a symlink, produce no event at all, and `vault sync` exits 0 with "0 conflict copies absorbed". A sibling package whose `vault.bin` is a symlink, by contrast, is reported as `UnsafePackageEntry` and the run ends "not converged". 03 §2 D-1 says such entries are `UnsafePackageEntry`, "never a silent fallback". Nothing is followed or absorbed. The behaviour predates this wave, but the wave's design is that every candidate that cannot be used gets reported once.
2. **L2: after lock and unlock, the app hides a save refusal that still stands (code read only, with library evidence).** Take a newer-version file that arrives while the vault is unlocked: the strip shows. The user then locks and unlocks. vault-sync emits nothing at lock or unlock, keeps refusing saves, and the password unlock succeeds. The app's `unlocked()` clears the strip with the comment "The unlock re-read the file; a refusal from before the lock no longer applies", which is not what happens. The user then sees the older items with no strip and no card until an edit's autosave is refused. If the same file arrives while the vault is locked, the card blocks the unlock entirely.

**The wave held on these inputs** (details under "What held up"):
- `UnreadableConflict` is emitted once per path and content for both conflict shapes and for versions 0, 3 and 0xFFFF.

- Version 0 never produces `NewerVersion`, unlocked or locked. `restore_from` follows the 03 §8 split.

## Findings

### L1 (fixed in vault-sync 2026-11-21: unsafe entries → `UnreadableConflict` once): Symlinked or FIFO conflict candidates are skipped without any report

- **Severity:** low
- **Crate and file:** vault-sync `crates/vault-sync/src/synced/reconcile.rs`:
  - `:411-417`: `on_file_conflict` handles `match fs::symlink_metadata(path) { Ok(m) if m.is_file() => {} _ => { self.forget_sibling(path); return; } }`.
  - `:442-449`: the same pattern with `is_dir()` in `on_package_conflict`.
- **Expected:**
  - 03 §2, "Not following links (2026-11-06, D-1)": "every file the package opens (`.lock`, `vault.bin`, backups, blobs, conflict-copy sources) is opened with `O_NOFOLLOW` and must be a regular file after `fstat`; a symlink or special file is `UnsafePackageEntry`, never a silent fallback".
  - 03 §6 step 1 (2026-11-21): a candidate that cannot be used is reported ("`vault sync` reports it and exits 'not converged'").
  - 00 phase 1: `sync` "fails with 'not converged' if any problem was reported".
- **Observed:**
  - These candidates produce no `SyncEvent` (`cf21`), and `vault sync` prints "synced: 0 conflict copies absorbed" and exits 0 (`run_all.sh`, three runs):
    - `vault 2.bin` as a symlink to a valid copy of our vault;
    - `vault 7.bin` as a FIFO;
    - `<name> 4.vault` as a symlink to a package directory.
  - A sibling package whose `vault.bin` is a symlink gives "… is a symlink, not a regular file, or was swapped while in use; refusing to use it" and "not converged" (exit 1).
  - In every case nothing is followed, merged, moved or deleted.
- **Why it matters:**
  - Nothing is lost and nothing is followed, which is the important half of D-1.
  - The other half fails: the user (app) and the script (CLI exit code) are told nothing about a conflict candidate that the build refuses to use.
  - The two package shapes behave differently for the same hazard.
  - The 2026-11-21 change exists to close exactly this kind of silent skip (last hunt's N1).
- **Reproduction:**
  ```sh
  cargo build -p vault-cli
  cd qa/spec-checks
  cargo test --test conflicts_1121 cf21                    # "symlink: no event at all", "fifo: …", "symlinked sibling package: …"
  ./cli/run_all.sh | grep -i 'skipped silently'           # rc 0 for all three shapes
  ```
  By hand: in a package, run `ln -s vault.bin "vault 6.bin"; vault sync; echo $?`. It prints `0`.
- **Suggested fix:**
  - For a candidate name that is present but not a regular file (per-file shape) or not a real directory (package shape), report once per path, without opening it.
  - Report it either as `UnreadableConflict(path)` or as `Error(UnsafePackageEntry)`. If it is `UnreadableConflict`, the CLI and the app need no change.
  - Keep `forget_sibling` for the case where the entry is gone.
  - Add the three shapes to `crates/vault-sync/tests/watch.rs`.

### L2 (fixed 2026-11-21: `SyncedVault::save_blocked()` getter; the app re-raises the strip after unlock): After lock and unlock, the app clears the save-blocked strip although vault-sync still refuses saves (code read only, library evidence)

- **Severity:** low
- **Crate and file:**
  - vault-app `crates/vault-app/src/state.rs:1150-1157`: `unlocked()` calls `clear_save_blocked()` under the comment "The unlock re-read the file; a refusal from before the lock no longer applies".
  - vault-app `crates/vault-app/src/state/sync.rs:420`: the locked-time card is raised only for a `SaveBlocked(NewerVersion)` report received while `locked`.
  - Library behaviour from vault-sync `crates/vault-sync/src/synced/reconcile.rs:344-348` (`set_save_blocked` emits only when the block is new) and `crates/vault-sync/src/synced.rs` `lock()`, which keeps `save_blocked`.
- **Expected:**
  - 05 §2.3 "Save-blocked strip": "while saves are failing with … a save-refused event: newer app version wrote the file … the main window shows a danger strip".
  - 05 §2.2 (2026-11-21, N2): the card exists because a newer file "would otherwise go unnoticed".
  - 03 §8: `SaveBlocked` is "emitted once at first detection and once per refused save".
  - The same 05 §2.3 paragraph also says the strip "disappears … after an unlock", so the spec pulls both ways.
- **Observed:**
  - `cf22`, run on two handles on one folder. A version 3 file arrives while unlocked: one `SaveBlocked(NewerVersion(3))`. Then `lock()` returns `Snapshotted`, and there is no new event. `unlock(password)` returns Ok, and there is no new event. The next save is refused, and `SaveBlocked` is emitted for the second time. The newer file is intact.
  - In the app, then:
    - the strip shown before the lock is cleared by `unlocked()`;
    - no card is raised, because nothing was reported while `locked`;
    - the user sees the last readable items with no hint until an edit's autosave is refused.
  - With the same file arriving while locked instead (`cf15`), vault-sync reports during the lock and the app's card hides the password field and Touch ID, so the vault cannot be unlocked at all.
  - So the same on-disk state gives "blocked" or "silently stale" depending on whether the file arrived before or after the lock.
  - The comment in `unlocked()` does not match vault-sync. The unlock does not re-read unchanged bytes, and the refusal still applies.
- **Why it matters:**
  - This is the N2 symptom of the last hunt ("the user sees the older items with no hint"), still present on the other ordering.
  - Nothing is lost: saves are refused and the newer file is kept. The cost is a misleading UI and, for an edit made after unlocking, a surprise refusal.
- **Reproduction:**
  ```sh
  cd qa/spec-checks
  cargo test --test conflicts_1121 cf22 -- --nocapture   # SaveBlocked counts: detection 1, after lock 1, after unlock 1, after a refused save 2
  cargo test --test conflicts_1121 cf15 -- --nocapture   # arrival while locked: SaveBlocked(NewerVersion(3)) reported during the lock
  grep -n 'a refusal from before the lock' ../../crates/vault-app/src/state.rs
  ```
- **Suggested fix:**
  - Let vault-sync expose the standing block (for example `SyncedVault::save_blocked() -> Option<SaveBlocked>`), or re-emit `SaveBlocked` once after an unlock while a block stands.
  - In `unlocked()`, keep the strip when a block stands, or raise the card at lock time for `NewerVersion`, whichever the owner prefers.
  - Amend 05 §2.3 "after an unlock" to "after an unlock that finds a writable file".

## What held up

These checks passed on the inputs listed. They show the behaviour on those inputs; they are not proofs.

**Unreadable conflict copies (03 §6 step 1, §8 `UnreadableConflict`):**
- **Per-file copy, once per content (`cf01`):** a random-bytes `vault 2.bin` gives exactly one `UnreadableConflict(<pkg>/vault 2.bin)`.
  - Two re-deliveries of the same bytes (new inode and mtime) stay silent.
  - Other bytes give a second event, and their re-delivery stays silent.
  - The copy stays in place, `vault.bin` is unchanged, the in-memory items are unchanged and not dirty, and there is no `Merged`, `ConflictAbsorbed` or `Error`.
- **Versions and damage (`cf02`):** these each give exactly one event, stay byte-identical in place, never raise `SaveBlocked`, and a save afterwards succeeds:
  - version 0, version 3 and 0xFFFF copies of our own file;
  - a half-length copy;
  - a version-0 copy under the Dropbox pattern;
  - `VAULT 6.BIN` (case-insensitive name).
- **Sibling packages (`cf03`):** a garbage or version 3 `vault.bin` in `<name> 2.vault` / `3.vault` gives one event each, naming the package.
  - A rewrite of the same bytes stays silent, and so does a late blob in its `attachments/`.
  - The app toast takes the file name, so it shows "w 2.vault", not "vault.bin".
- **Readable later (`cf04`):** a garbage copy that is replaced by a valid copy is absorbed:
  - its item is merged;
  - the file moves to `backups/conflict-…-vault 2.vault.bin`;
  - there is no second unreadable report.
  - The same garbage at the same path afterwards is reported again.
- **Reset points:**
  - The copy is reported again after it disappears, for both shapes (`cf05`).
  - It is reported again at the unlock after a lock, without any new file event, and a same-bytes re-delivery afterwards stays silent, for exactly 2 reports (`cf06`).
  - It is reported again after stop/start watching (`cf07`).
  - Two paths with identical bytes give one event each (`cf08`).
- **Non-candidates (`cf09`):** garbage in these places gives no event:
  - `notes.bin`, `vault.bin.bak`;
  - `backups/*.vault.bin`, `.vault.bin.tmp-*`, `attachments/*.bin`;
  - a deeper `deeper/vault 2.bin`;
  - a non-`.vault` sibling directory.
- **Download in progress (`cf10`):** with `ensure_downloaded` failing for the copy, it gives `CloudUnavailable` and no `UnreadableConflict`. Once downloadable and valid, it is absorbed.
- **Bookkeeping side by side (`cf11`):** a foreign sibling, a package waiting for a blob and an unreadable per-file copy, each rewritten twice, give exactly one `ForeignVault`, one `WaitingForBlobs` and one `UnreadableConflict`.
  - The late blob brings `ConflictAbsorbed` for the waiting package.
  - The foreign sibling and the unreadable copy stay.
  - Absorbing the waiting package does not re-report the unreadable copy.
- **Sibling sequences:**
  - A sibling that is first unreadable, then valid but waiting for a blob, then complete gives one `UnreadableConflict`, one `WaitingForBlobs` and then `ConflictAbsorbed` (`cf12`).
  - An empty sibling directory is neither reported nor moved before its `vault.bin` arrives, and is absorbed afterwards (`cf13`).
- **Restore (`cf14`):** `restore_from` with an unreadable copy in the package succeeds and leaves the copy byte-identical. No repeated reports follow.
- **Many copies (`cf18`):** 40 unreadable copies drain in 6 polls (2.3 s) with exactly 40 events.
- **`vault sync` (`run_all.sh`):**
  - With a garbage per-file copy it exits 1 and prints "unreadable conflict copy: <path>" and "error: not converged" on two consecutive runs. The copy stays byte-identical, `vault.bin` is untouched, and the master password never appears in the output.
  - The same holds for versions 0, 3 and 0xFFFF and for a garbage sibling package.
  - A valid copy next to a garbage one is absorbed (its item is listed), and the run still exits 1. Once the garbage copy is removed, the run exits 0.
  - 20 garbage copies: the run exits 1 within a second and all 20 are named and kept.
  - 4 concurrent `add` and 2 concurrent `sync` with a garbage copy present: every add is kept, both syncs exit 1, and the copy is kept.
  - A 65 MiB copy: the run exits 1 and the copy is kept.
  - Control bytes in a copy's name are escaped (`\u{1b}`). This was a manual probe, not a ledger check.

**Version 0 vs newer (03 §3 L3, §8 `restore_from`; ra01/ra17/ra22/ra23 still pass):**
- **Unlocked (`cf15`):** a version-0 primary gives `CorruptOnDisk` and never `NewerVersion`. The in-memory state is kept, and the next save rewrites a valid version 2 file (03 §9).
  - Versions 3 and 0xFFFF give `SaveBlocked(NewerVersion(v))`. The save is refused and the file is kept.
- **Locked (`cf15`):** a version-0 primary gives `CorruptOnDisk` and no `NewerVersion`, so the app's locked-time card is not raised for damage.

  - Over a version 3 primary, the restore returns `NewerVersion`, and the file is untouched.
- **CLI:** for a version-0 file it still says "unsupported vault format version 0" without a panic. For a copy whose first item was altered it now says "vault file has been tampered with: Item(…)" (last hunt's L1 holds through the CLI).

**vault-sync code read (this wave):**
- **The memory:** `unreadable_conflicts` maps the path key to (path, blake3 of the bytes read).
  - An entry is removed when the candidate parses, vanishes, loses its `vault.bin`, or is absorbed (`forget_sibling`).
  - The map is cleared by `start_watching` and `stop_watching`, and taken by `lock()` into `pending_conflicts` for the post-unlock re-check.
  - It is bounded by the distinct candidates on disk.
- **Attacker-controlled sizes:** the bytes are read through the existing 64 MiB capped, no-follow reader before parsing. Parsing, with no decryption, runs before any key is involved. The only new work before a key check is hashing at most 64 MiB.

## Notes

These are spec ambiguities and observations. They are not counted as bugs.

- **N1. An oversized or I/O-failing conflict copy is reported as `SyncEvent::Error` on every event, not once.**
  - A 65 MiB `vault 2.bin` gives `Error("<path> is too large to be a vault file")`. Two re-deliveries of the same bytes raise the count from 1 to 3 (`cf17`), and the app toasts each one.
  - 03 §6 step 1 names only "does not parse" and "unsupported format version". The vault-sync doc comment deliberately routes these cases to `Error`. Consider the same once-per-content memory for them.
- **N2. 03 §8 can be read two ways for A→B→A.**
  - "Emitted once per path and content" suggests a set of contents. "(re-emitted when the bytes change …)" suggests only the last content counts.
  - The code keeps only the last content, so A, B, A gives 3 events (`cf01`). The check records this and does not assert either reading.
- **N3 (fixed 2026-11-21). A copy first reported while locked is not reported again at the next unlock.**
  - A copy reported before the lock is reported again at unlock. One that arrives and is reported during the lock is not (`cf06`: 1 → 1). This follows from `lock()` emptying the memory before the copy arrives.
  - The app's toast shows on the lock screen, so the user is told once. The spec phrase "again after lock/unlock" does not say which applies.
- **N4. The locked-time card outlives its cause (code read only).**
  - If the newer file is replaced by a readable one while locked, vault-sync lifts its block silently (no event), but `unlock_blocked` stays.
  - The user must use "Open another vault…" and reopen the same vault. 05 §2.2 says the card "is cleared only by a successful unlock or by opening another vault", so this matches the spec. It is an extra step.
- **N5 (fixed 2026-11-21: `text::sanitize_line`, 60-char cut; toast now in 05 §2.3). The unreadable-copy toast is not in 05, and its file name is not sanitised (code read only).**
  - 05 does not describe the toast at all (only 03 says the event is emitted). The toast text and its "file name only" rule live only in code.
  - The name is shown as delivered: a newline or a bidi override in a peer-created file name reaches the pill. The CLI escapes the same name.
