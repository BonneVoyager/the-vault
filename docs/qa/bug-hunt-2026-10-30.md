# Bug hunt 2026-10-30

Independent, spec-derived test run against the current tree. The checks were written from `specs/00`–`05` and `README.md` before reading the source, the project's tests or `PROGRESS.md`. They live in `qa/spec-checks/`, a standalone crate, with black-box CLI checks in `qa/spec-checks/cli/run_all.sh`.

## Summary

There were no high- or medium-severity findings. The format, crypto, tamper detection, merge, sync, conflict absorption, backups, attachments and importers behaved as specified on every input tried. That includes hostile KDF parameters, hostile CBOR sizes, every truncation offset, random bit flips, hostile KDBX headers and a 1PUX decompression bomb.

Four low-severity findings remain:

- Vaults are created with `created_at = 0`.
- A refused save is not reported as a `SaveBlocked` event.
- A key rotation on another device is first reported as `KeyMismatch`.
- The README and spec 01 still describe the old sibling-file layout.

The project's own suite is green.

## Findings

### L1. New vaults record `created_at = 0` in the header and in the password slot

- **Severity:** low
- **Where:** vault-sync, `crates/vault-sync/src/synced.rs:161`. `SyncedVault::create` calls `UnlockedVault::create`, which stamps 0 (`crates/vault-core/src/vault.rs:388-397`). The core already has `create_with_created_at`. The CLI and the app both create vaults through `SyncedVault::create`.
- **Expected:** 01 §2 says `"created_at": u64 unix seconds`, and the KeySlot also carries `"created_at": u64`. 00 lists "vault creation time" among the accepted leaks of the format.
- **Observed:** a vault created with `vault init` or `SyncedVault::create` has header `created_at = 0` and slot `created_at = 0`.
- **Why it matters:** the only creation timestamp the format carries is wrong for every real vault. Anything that later shows or sorts by creation time will be wrong. This matters especially because the field cannot be repaired after the fact without a format-level migration.
- **Reproduction:**
  ```sh
  cargo build -p vault-cli
  cd qa/spec-checks
  cargo test --test cli_bridge b01_cli_init_header_created_at
  cargo test --test sync s01_save_layout
  ```
- **Suggested fix:** in `SyncedVault::create`, call `UnlockedVault::create_with_created_at` with the current unix seconds. Add a sync test that asserts a non-zero header and slot `created_at`.

### L2. A save refused for a newer format version or a foreign vault is not a `SyncEvent::SaveBlocked`

- **Severity:** low
- **Where:** vault-sync, `crates/vault-sync/src/event.rs:11`, which has no `SaveBlocked` variant. The refusal is `SyncError::SaveBlocked` (`crates/vault-sync/src/error.rs:51`, `:99`). The watcher path reports it through `emit_error` (`crates/vault-sync/src/synced/reconcile.rs:91`, `:153`).
- **Expected:** 03 §3 says "the save is refused with `SyncEvent::SaveBlocked{NewerVersion | ForeignVault}` and the in-memory state is kept". 03 §8 lists `SaveBlocked(SaveBlockReason)` among the `SyncEvent` variants.
- **Observed:** `save()` returns `Err(SaveBlocked(NewerVersion(2)))`. The subscriber stream only carries `Error("the vault file was written by a newer version (format 2); update this app")`. The behaviour is otherwise correct: the file is untouched and the in-memory state is kept.
- **Why it matters:** an event consumer cannot tell "update the app" or "this is a different vault" apart from other errors without matching on display text. The app's banner logic for this case therefore rests on string content.
- **Reproduction:**
  ```sh
  cd qa/spec-checks
  cargo test --test sync s09b_save_blocked_is_an_event
  ```
- **Suggested fix:** add `SyncEvent::SaveBlocked(SaveBlocked)` and emit it wherever the watcher or the pre-write merge detects the block. Alternatively, change 03 §3 and §8 to describe the error-only design.

### L3. A key rotation on another device is reported as `KeyMismatch`, not `KeyRotatedOnDisk`

- **Severity:** low
- **Where:** vault-sync, `crates/vault-sync/src/synced/reconcile.rs:128-135` emits `KeyMismatch`. `KeyRotatedOnDisk` is only emitted after a later `unlock(password)` (`reconcile.rs:545`).
- **Expected:** 03 §8 defines `KeyMismatch` as "password changed elsewhere" and `KeyRotatedOnDisk` as "vault_key rotated elsewhere; must re-unlock with the password". 03 §5 says "a key rotation is detected as before (`KeyRotatedOnDisk`)".
- **Observed:** after device B rotates the vault key, device A's watcher emits `KeyMismatch`. After the header merge, a password change no longer changes the vault key, so it never causes a mismatch. `KeyRotatedOnDisk` follows only after the user re-enters the password, together with `Merged`. That two-step flow works and keeps A's unsaved edits; check `s15c` passes. It is documented in `event.rs`, but not in the spec.
- **Why it matters:** the spec's event meanings are now reversed in practice. A UI written from the spec would show "password changed elsewhere" for a rotation and would treat `KeyRotatedOnDisk` as a prompt rather than a confirmation.
- **Reproduction:**
  ```sh
  cd qa/spec-checks
  cargo test --test sync s15b_key_rotation_event_kind
  ```
- **Suggested fix:** update 03 §5 and §8 to the implemented semantics. `KeyMismatch` means "on-disk file does not open with our key: rotation, rollback to empty, or tamper; ask for the password". `KeyRotatedOnDisk` means "re-verified and adopted". Alternatively, rename the events to match the spec.

### L4. README and spec 01 still describe the pre-package file layout

- **Severity:** low (documentation)
- **Where:** `README.md:78-82` ("Vault file layout"). `specs/01-vault-format.md:3` and `:128` give attachments as `<name>.vault.attachments/<id>.bin`.
- **Expected:** 03 §1 (decided 2026-10-30) says `<name>.vault/` is a package containing `vault.bin`, `attachments/` and `backups/`.
- **Observed:** the binaries write the package layout; the CLI and sync checks confirm it. The README tells users the vault is a file with `.backups/` and `.attachments/` siblings.
- **Why it matters:** users decide what to copy and back up from the README. Attachments are explicitly not in the backups, so pointing users at the wrong paths is a data-loss risk when they move a vault by hand.
- **Reproduction:**
  ```sh
  grep -n "vault.attachments\|vault.backups" README.md specs/01-vault-format.md
  ```
- **Suggested fix:** replace the README section with the 03 §1 package layout. Update 01's opening line and the attachment path in §4 to `<name>.vault/attachments/<id hex>.bin`.

## What held up

Each item below held on the inputs tried. That shows the behaviour on those inputs, not a proof.

- **Format (01 §1-§4):** layout and canonical CBOR are correct. An independent decoder opens core-, CLI- and sync-written files with only the spec's AADs, HKDF labels and NFC rule; that covers slot unwrap for password and enclave slots, items, the manifest, `header_digest` and attachment chunks. The manifest is sorted by id. ItemPlain omits `kind`.
- **Parser rejections:** wrong magic, version > 1, `header_len` beyond EOF or `u32::MAX`, and trailing bytes are all rejected.
- **Tamper detection:** every byte of every item ciphertext was flipped and reported as `Tampered(Item(id))`. Nonce and `modified_at` edits are detected. Drop, rollback, duplicate, misplaced, missing and extra manifest records are detected. An item moved between vaults is detected. A `vault_id`, KDF or salt edit gives `WrongPassword`, as 01 §7 describes. Stripped, bumped or forged header stamps give `Tampered(Manifest)` on the key path.
- **Corruption sweeps:** every truncation offset failed cleanly. 1,500 random single- and multi-bit flips gave no panic, hang or silent change. Hostile CBOR was tried in a child process with time and RSS limits: 200k-deep nesting, `2^62`-length arrays and byte strings, `u32::MAX` slot counts and `2^40`-byte keys. Every case returned an error quickly with bounded memory.
- **Hostile KDF parameters:** `m_cost` above 1 GiB, `t_cost` above 16, `p_cost` above 64, zero costs, wrong types and wrong `alg` are refused at parse, before Argon2. An unknown slot kind gives `NoUsableSlot` before Argon2.
- **Keys and slots:** guarantee 8 (`change_password` keeps the vault key) holds. The last password slot cannot be removed. Rotation drops enclave slots. NFC normalisation works. Duplicate slot ids give `Malformed`. Opaque slots are kept in place. A coarse timing comparison of wrong passwords showed no early exit.
- **Merge (03 §5):** every table row holds, including tombstone versus later edit, field LWW, the `device_id` tie-break and metadata LWW. History union and `removed_history`, the attachment union and removal tombstones, monotone stamps and the `update` diff bump all hold. 60 seeded random edit scripts on two and three devices (skew, ties, deletes, resurrects) were commutative on content, idempotent, and identical after two rounds. Header LWW is monotone under clock skew.
- **Sync:** two handles on one package converge through the watcher, including with unsaved edits. Delete-versus-edit resolves both ways. Both conflict-copy shapes are absorbed and moved to `backups/conflict-*`: iCloud sibling packages (`x 2.vault`, conflicted copies, uppercase) and in-package `vault 2.bin` / `vault (… conflicted copy …).bin`.
  - Foreign copies are left untouched.
  - Copies arriving while locked are deferred to the next unlock.
  - Whole-package moves wait for missing blobs and are re-triggered by a late blob.
  - A conflict copy carrying a password change is adopted.
  - Forged-header and unopenable copies are never deleted.
- **Sync failure handling:** a corrupt primary gives `CorruptOnDisk` and the next save repairs it. A newer version or foreign vault on disk is never overwritten. A same-size external write with a forged mtime is still merged (V-05), both in place and by rename. `CloudHooks` are called before reads, pin runs after open, an evicted blob shows as `NotDownloaded`, and a timeout does not overwrite.
- **Concurrent writers:** 2 threads × 15 saves and 12 parallel `vault add` processes lost no items and left no tmp files.
- **Backups and attachments:**
  - Backup policy holds: first save after unlock, one per hour, and an extra one when the item count drops. Snapshots are the exact written bytes.
  - Retention bucket bounds held over 200 synthetic snapshots, and `Conflict` backups were not pruned.
  - `restore_from` works when the primary does not parse, snapshots the current file first, and refuses a foreign vault.
  - Unsaved edits at lock land in an `-unsaved` backup.
  - Attachments: sizes 0, 1, 1 MiB ± 1 and 3 MiB round-trip, and chunk AADs match an independent decrypt. Swap, reorder, truncation, extension, flips and an empty blob are all detected. The over-100 MB cap is enforced before encryption. Orphan cleanup respects the 24 h grace and keeps blobs referenced by tombstones.
  - File modes are 0600 for `vault.bin`, blobs, backups and `.lock`, and 0700 for `attachments/` and `backups/`.
- **TOTP and generator:** TOTP matches the RFC 6238 Appendix B vectors (SHA1/256/512) and 300 independent HMAC computations. Those covered 6/7/8 digits, periods from 1 s to 3600 s, and 1- to 64-byte secrets, so there is no minimum length. Secret normalisation and scheme/host case-insensitivity work, and hotp is rejected. No hostile URI panicked, including `period=0`. The generator's class guarantee holds at length 4, `exclude_ambiguous` removes `0O1lI|`, the character distribution is roughly uniform, and the EFF list is in use. Search ranking order, Unicode folding and filters work, and password values never match.
- **Importers:**
  - CSV export and import round-trip commas, quotes, newlines and Unicode, give fresh ids and the importer's stamps, and leave out tombstones. Hostile CSV does not panic.
  - KDBX imports map fields, keep protected custom fields concealed and map `otp` to TOTP. A wrong password gives a generic error without the password. The 100 MiB and 1 MiB limits are enforced. Hostile KDF headers in KDBX 4 (Argon2 memory 4–64 GiB, iterations 2^32, parallelism 2^24, AES-KDF 2^40 rounds) are refused in under 0.5 s.
  - 1PUX: a 2 GB decompression bomb stayed at a peak RSS of about 140 MB and failed cleanly.
- **CLI:** weak master passwords are refused unless `--allow-weak`, and `init` will not overwrite. `get` hides the password without `--reveal`. Template tags work. The TOTP code matches an independent Python HMAC. Errors exit cleanly with no panic exit code and never echo the password. Export needs `--yes`, is created at 0600, refuses to overwrite without `--force`, and `--force` tightens an existing 0644 file to 0600. `attach get` writes 0600 and refuses to overwrite. Truncated vaults are never rewritten.
- **Security read:**
  - Only RustCrypto primitives and `OsRng` are used, with fresh 24-byte nonces.
  - Keys sit in `Zeroizing`, and the NFC copy of the password is zeroized.
  - `Debug` is redacted on `Field`, `HistoryEntry`, `AttachmentRef`, `Item` and `UnlockedVault`.
  - There is no `unsafe` outside vault-macos, and core and sync `forbid` it. There are no secret-dependent comparisons on an attacker oracle.
  - Error and log texts carry positions, kinds and paths, not values.
  - The vault-macos Keychain code matches 04 §2 (code read only): `WhenUnlockedThisDeviceOnly`, `PrivateKeyUsage | BiometryCurrentSet`, Secure Enclave token, ECIES cofactor X9.63 AES-GCM, and `kSecAttrSynchronizable = false`.
  - Pasteboard writes follow 04 §3 (code read only): `CurrentHostOnly`, then the concealed marker before plain text, with clear-on-failure.
  - The Touch ID policy is fail-closed on an unreadable boot time and enforces 7 days and 5 failures (vault-app, code read only).
  - Lock clears the clipboard, closes windows and saves first (vault-app, code read only).
  - `VAULT_ALLOW_SCREEN_CAPTURE` is honoured only in debug builds (code read only).

## Notes

None of these are counted as bugs.

- **API drift from 02:** `merge_from` returns `Result<MergeReport, VaultError>`, which is reasonable given "same vault_id (else error)". The slot mutators (`change_password`, `add_enclave_slot`, `remove_slot`, `rotate_vault_key`) take a `now` for the header stamp. `unlock_with_key` takes a device id. `Field` has `extras`. The spec signatures predate the header stamp.
- **KDF cost:** 02 says "Argon2 runs once per slot". The implementation derives the KEK once per unlock, because all password slots share one `kdf` map. That is better than the spec, and slot count cannot amplify cost.
- **Residual KDF ceiling:** caps of m ≤ 1 GiB, t ≤ 16 and p ≤ 64 still let a file-writing attacker make each unlock attempt allocate 1 GiB and run 16 passes. That is bounded, and anyone who can write the file can corrupt it anyway.
- **Convergence timing:** after a same-stamp tie, item `modified_at` can differ by 1 between devices after one round and is identical after two. This matches 03 §5's "within two merge rounds".
- **Clean saves:** a clean `save()` is a no-op and does not re-read the primary, so a handle without a watcher learns about other writers only on its next dirty save or watcher event. 03 does not require otherwise.
- **Corrupt-looking newer versions:** a corrupt primary whose bytes 4–5 happen to decode as a large version number is treated as "newer version" and blocks saves, rather than giving `CorruptOnDisk`. This is the safe direction.
- **Backup names:** the files are `<name>-<ts>.vault.bin`, with `-2`, `-3` suffixes for snapshots in the same second and `-unsaved` for unsaved ones. 03 §1 shows `.vault.bin` while 03 §4 says `.vault`. Lexical order of same-second names is not chronological.
- **Passphrases:** the EFF large list contains hyphenated words such as "drop-down" and "felt-tip". With the default `-` separator, a passphrase cannot be split back into words. The effect on entropy is negligible.
- **1PUX leniency:** well-formed but oddly shaped 1PUX JSON, such as `{"accounts": 5}` or a `null` item, imports as 0 items rather than an error.
- **KDBX terminator:** the `keepass` parser accepts a KDBX 4 stream without its empty terminating HMAC block. Every entry is still present and authenticated, so no data is dropped.
- **`export --force`:** it writes through a symlink at `--out`, and fixes the mode after opening the file. A process that already held the old file open could read the new contents. Both behaviours are inherent to overwriting a user-chosen path. Writing a fresh 0600 temp file and renaming it over the target would close both.
- **Minimum macOS version:** 04 §7 step 2 says `LSMinimumSystemVersion 14.0`, while 00, 04's header and `scripts/Info.plist` say 15.0. The script is right and the spec line is stale.
- **Search copies:** `search` builds non-zeroized, case-folded copies of notes and usernames per query. These are not secret kinds under CLAUDE.md.
- **Touch ID policy storage:** the policy (last password unlock and failure counter) is kept in an app-support file that the user can write (code read only). Same-user malware is out of scope per 00.

## Limits

- **Platforms not driven:** vault-macos and vault-app were not driven. Their findings are code read only, and Touch ID, Keychain, pasteboard and iCloud were not exercised.
- **API discovery:** to compile the checks I learned public signatures from compiler errors and from `pub` lines in `attachment.rs`, `event.rs`, `error.rs` and `cloud.rs`. I did not read implementations before the checks were written.
- **Watcher timing:** the sync checks rely on FSEvents with a 500 ms debounce on one local APFS volume. Real cloud providers, network volumes, coarse timestamp filesystems and eviction were not tested.
- **Retention:** checked with synthetic file names and the default multiplier only. The 0.5×–4× multipliers and the 36-month cap at full depth were not exercised.
- **Randomised checks:** fixed seeds were used for bit flips and merge scripts. These are bounded samples, not fuzzing. No `cargo-fuzz` or property-test shrinking was run.
- **Timing:** the wrong-password timing check is a coarse ratio on one machine. It is not a side-channel measurement.
- **Not tested:** passkey slots (not implemented), the 1PUX field mapping beyond hostile inputs, and KDBX 3 files (the `keepass` crate cannot write them).
