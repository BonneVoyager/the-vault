## Findings

### L1 (fixed in code 2026-11-21): On the vault-key path, a tampered *first* item record is reported as a wrong key

- **Severity:** low
- **Crate and file:**
  - vault-core `crates/vault-core/src/vault.rs:287-307` (`first_failure_is_wrong_key && pairs.is_empty()` passed to `tag_failure` at `:81`);
  - effects in vault-sync `crates/vault-sync/src/event.rs:27-29` (`KeyMismatch`) and `crates/vault-sync/src/synced/reconcile.rs:572`;
  - effects in vault-app `crates/vault-app/src/state/sync.rs:416-422`.
- **Expected:**
  - 02 guarantee 4: "Flipping any byte in any item `ct` → `Tampered(Item(id))`."
  - 01 §7: "Report `WrongPassword` when at least one password slot exists and all fail".
  - The realigned 02 signature comment says `unlock_with_key` maps the "first tag failure → WrongPassword". That makes 02 contradict its own guarantee 4.
  - 03 §8 describes `KeyMismatch` as "on-disk file no longer opens with our cached key (password changed elsewhere)".
- **Observed:**
  - With the right vault key, flipping one byte in record 0 of 3 gives `WrongPassword` via `unlock_with_key`, and `Tampered(Item(id))` via `unlock` (`ra17`).
  - Records 1 and 2 give `Tampered(Item(id))` on both paths.
  - Two handles on one folder (`ra22`), with the file altered on disk:
    - record 0 altered → `KeyMismatch`;
    - record 1 altered → `CorruptOnDisk`.
  - `vault sync` with a per-file copy whose first record was altered prints "error: could not merge <copy>: wrong password" and then "not converged" (`run_all.sh`).
  - The vault-core doc comment states the mapping is deliberate. A wrong key and a tampered first record are indistinguishable when only that record is tried.
- **Why it matters:**
  - Identical damage gets two different user stories, depending on which record it hits.
  - Damage to the first record (which a file-writing attacker can choose) sends the app into the "key changed on another Mac, enter your password" prompt, with saves refused, instead of the integrity message.
  - After the user types the password, the unlock fails as `Tampered`.
  - Nothing is accepted or overwritten, so the impact is misleading messages and a forced password prompt.
  - The spec now states two incompatible rules.
- **Reproduction:**
  ```sh
  cargo build -p vault-cli
  cd qa/spec-checks
  cargo test --test realign_1121 ra17 -- --nocapture   # record 0: key path WrongPassword; records 1-2: Tampered(Item)
  cargo test --test realign_1121 ra22 -- --nocapture   # record 0 -> KeyMismatch; record 1 -> CorruptOnDisk
  ./cli/run_all.sh | grep 'first item was altered'      # "could not merge ...: wrong password"
  ```
- **Suggested fix:**
  - When the first item tag fails on the key path, try the manifest with the same key before deciding.
  - If the manifest opens, the key is right: report `Tampered(Item(id))`. Report `WrongPassword` only when both fail. The empty-vault case stays as it is.
  - Then restate guarantee 4 as holding on every path. Alternatively, keep the code and amend guarantee 4 and the 03 §8 `KeyMismatch` text to say a damaged first record is indistinguishable from a key change.

## What held up

## Notes

These are spec ambiguities and observations. They are not counted as bugs.

- **N1 (fixed 2026-11-21: `SyncEvent::UnreadableConflict`, CLI reports it as not converged). Unparseable or newer-version per-file conflict copies are skipped silently.**
  - A random-bytes `vault 2.bin`, a truncated copy of our own `vault.bin`, and a copy with version 3 all leave the file in place. No event is emitted, and `vault sync` prints "synced: 0 conflict copies absorbed" and exits 0.
  - 03 §6 defines only the foreign-`vault_id` case. 00's "fails with 'not converged' if any problem was reported" holds, because nothing is reported.
  - A copy that a provider is still downloading should indeed wait. A permanently broken copy, however, is never surfaced to the user.
  - Consider a one-time `SyncEvent` for an unreadable conflict candidate.
- **N2 (fixed 2026-11-21: the locked-time event raises the card). A newer-version file arriving while locked does not raise the 2026-11-19 card.**
  - vault-sync emits `SaveBlocked(NewerVersion)` while locked. The next unlock (password or Touch ID key) opens the last readable copy (`ra23`).
  - 05 §2.2 scopes the card to "`UnsupportedVersion` on open". The save-blocked strip, raised by the locked-time event, is cleared by the unlock (05 §2.3, "after an unlock"), and returns at the next refused save.
  - Meanwhile the user sees the older items with no hint. Nothing is lost: the save is refused and the newer file is kept.
- **N3 (fixed 2026-11-21). The Touch ID completion has no `unlock_blocked` branch.**
  - The completion is `state/touch_id.rs:355-370`, and `AppState.error` is rendered only on the Choose screen.
  - If a Touch ID unlock ever returned `UnsupportedVersion`, the failure would be silent and the controls would stay. In the sequences driven here the unlock never returned it (see N2), so this is code read only.
- **N4 (owner 2026-11-21: accepted; a fit that included the editor chrome widened every read-mode column and was reverted). The edit-mode name input is narrower than the width it was fitted for (code read only, not measured).**
  - The editor's label column holds the grip (16 px), a 4 px gap, the field-icon button, another 4 px gap and the input with its padding (`editor.rs:1105-1121`, `:858-866`).
  - Yet `label_fit` sizes it for read mode's text alone, in regular weight, while the name input is medium weight. So the longest name is clipped by roughly 40–60 px while editing.
  - 05 requires equal read and edit columns ("Pressing Edit must not move any row"), so this follows the spec. But "so it grows while a name is typed" does not make the typed name visible.
  - The wave's tests assert column equality, not that the name is visible.
- **N5 (spec fixed 2026-11-21). 01 §4 says "all committed fixtures" lack `slots_modified_at`, but 7 of the 11 named fixtures carry it.**
  - Stamped: `v1-stamped`, `v1-icon`, `v1-meta`, `v2-basic`, `v2-field-icon`, `v2-meta`, `v2-trash-legacy` (`ra21`). The sentence predates the realignment, which left it in place.
- **N6 (fixed 2026-11-21, see PROGRESS.md for the colours). The danger pill's text contrast is low.**

## Limits

- **vault-app and vault-macos were not driven.** All app statements are code read only; no GUI was run. The label-column clipping in N4 was estimated from the layout code, not measured.
- **Timing checks are machine-specific.** The Argon2-per-slot timing (`ra08`), the lock waits (`ra18`, CLI) and the conflict timestamps (`ra20`) are timing-based and ran on one Mac with `NoopHooks`.
- **Not run:**
  - KDBX Argon2 memory at exactly 1 GiB (it would allocate 1 GiB);
  - fuzzing (no format or importer change in this wave);
  - `cargo deny` and `cargo audit` (no manifest or lockfile change);
  - real iCloud Drive or Dropbox folders.
- **Little new effort went to vault-core and vault-sync.** They are unchanged since the last hunt, so they were covered by the existing ledger plus the sentences the realignment now asserts.
- **Test-time KDF parameters were used throughout**, except the deliberate heavier `t_cost` in `ra08`.
- **All temporary files were cleaned up.** They went under `qa/spec-checks/tmp/`, which is empty after the run.
