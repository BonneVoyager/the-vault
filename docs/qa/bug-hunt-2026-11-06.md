## Summary

The run found two medium findings and three low ones. There are no high findings.

**M1. A save can write a `vault.bin` that the same code then refuses to read.** The 64 MiB read cap (D-10) is not applied on the write path. What happens next:

- The next `open` fails with `PrimaryTooLarge`.
- The app therefore cannot open the vault, and so cannot reach `restore_from` either.
- A second device that has the vault open treats the file as corrupt and overwrites it on its next save. Every change in the oversize save is lost, including small ordinary items.

**M2. The app refuses any 1PUX over 64 MiB.** The cap was added in D-10. The core reads only `export.data` from the archive, but 1Password exports also carry document attachments under `files/`. A user whose 1Password account holds documents can exceed the cap and cannot import at all. The core imports a 70 MiB archive like this without trouble (`kh03`).

**Low findings:**

- **L1.** An item with no fields, history or attachments skips Recently Deleted when deleted and can never be recovered.
- **L2.** A KeePass database that opens with the correct password but whose content the parser rejects is still reported as `KdbxCredentials`, the error used for a wrong password.
- **L3.** The backup viewer reads backups through symlinks (code read only).

Everything else in scope held on the inputs tried. That includes:

- Every rule of the Recently Deleted core.
- The recover-vs-strip race.
- Symlink and FIFO refusal.

## Findings

### M1. A save can write a `vault.bin` over the 64 MiB read cap: the vault no longer opens, and a peer overwrites it

- **Severity:** medium
- **Crate / location:**
  - `vault-sync`, `crates/vault-sync/src/synced.rs:651-654`: `save_locked` serialises and re-parses but never checks the size.
  - `crates/vault-sync/src/synced.rs:296-309`: `open` reads through the cap and fails.
  - `crates/vault-sync/src/synced/reconcile.rs:176-184`: a peer handles `PrimaryTooLarge` as "Never a file we wrote" and marks the primary corrupt.
- **Expected:** 03 §2: "Reads of `vault.bin` are capped (64 MiB) and refuse larger files with a typed error before parsing." The save path's own comment (`synced.rs:651`) promises it "guarantees we never put bytes on disk that we could not read back". 03 §3 step 3 says an unreadable primary must not be overwritten: "If parse fails → emit SyncEvent::CorruptOnDisk, do NOT overwrite".
- **Observed:**
  - An item whose notes field is a little over 65 MiB is saved without error, giving a 68,158,828-byte `vault.bin`.
  - A second save on the same handle also succeeds.
  - `SyncedVault::open` + `unlock` then fails with `PrimaryTooLarge`, and so does the CLI.
  - With a second handle B watching (`rf15`), A's oversize save first reaches B as `CorruptOnDisk`. B then adds an item and saves. B's save succeeds and rewrites the primary as a 1,469-byte file without A's changes, including the ordinary item `small-from-A` that A saved in the same write.
- **Why it matters:**
  - Lockout: once the app quits it cannot open the vault again, because `open` fails before `restore_from` can be called. The snapshot taken by that save is just as oversized.
  - Silent loss: on a second Mac every change in the oversize save disappears without a conflict copy or warning.
  - Any write can trigger it: nothing in 01/02 limits note size or item count, and CSV/KDBX imports can bring in large notes.
  - Recovery is manual: the user has to replace `vault.bin` in Finder with an older snapshot from `backups/`.
- **Reproduction:**
  ```
  cargo build -p vault-cli
  cd qa/spec-checks && cargo test --test review_fixes -- rf07 rf15
  ```
- **Suggested fix:**
  - In `save_locked` (and in `create`, `restore_from` and the Unsaved-backup write), refuse to write when `bytes.len() > MAX_VAULT_FILE_SIZE`. Return a typed error (for example `VaultTooLarge`), keep the vault dirty and say so in the app.
  - Alternatively, make write and read caps consistent by enforcing a per-field or per-item limit in core.
  - Separately, treat `PrimaryTooLarge` on a peer as "not ours to overwrite" (like `SaveBlocked`) rather than as a corrupt file. That way a file another build wrote is never clobbered unmerged.

### M2. The app refuses any 1PUX over 64 MiB, although only `export.data` is read

- **Severity:** medium (a migration blocker; no data loss)
- **Crate / location:** `vault-app`, `crates/vault-app/src/bounded_read.rs:15` (`MAX_IMPORT_FILE_SIZE`) and `crates/vault-app/src/state/transfer.rs:220` (`import_1pux_from`). Code read only; the app cannot be driven.
- **Expected:** 02 `import_1pux(bytes, …)` "zip + JSON" with no input limit (02 lists limits only for KDBX: "database 100 MiB, key file 1 MiB"). 05 §2.5 offers 1PUX import.
- **Observed:**
  - `import_1pux_from` reads the whole archive through `read_capped(path, 64 MiB)` and refuses larger files with "file is larger than the 64 MiB limit".
  - The core opens the zip and reads only `export.data`, which is itself capped at `MAX_EXPORT_DATA`.
  - A 70 MiB 1PUX (a small `export.data` plus a 70 MiB `files/scan.pdf`) imports in core with peak RSS 75 MB (`kh03`).
- **Why it matters:** 1Password's 1PUX export includes document attachments under `files/`. A user moving from 1Password with a few scanned documents can easily pass 64 MiB, and then cannot import at all. The workaround (re-zipping the archive with only `export.data`) is not discoverable. This is exactly the "legitimate user hits a new bound" case the brief asked about.
- **Reproduction:** `cd qa/spec-checks && cargo test --test kdbx_hostile -- kh03 --nocapture` shows the core side. The app side is visible by reading `transfer.rs:213-228`.
- **Suggested fix:** do not slurp the archive. Open the zip from a `File` with `ZipArchive::new(BufReader<File>)`, and bound only what is extracted (the `export.data` cap already exists). If a whole-file cap is wanted, use the KDBX limit (100 MiB) or larger, and check `export.data`'s uncompressed size from the central directory first.

### L1. A deleted item without fields skips Recently Deleted and cannot be recovered

- **Severity:** low
- **Crate / location:** `vault-core`, `crates/vault-core/src/item.rs:454` (`has_content`); `crates/vault-core/src/vault.rs:1017` (`deleted_items`) and `:956` (`recover` refuses "has no content").
- **Expected:** 05 §2.3: "`⌘⌫` in All Items keeps its confirm sheet; its body gains 'You can recover it from Recently Deleted for 30 days.'" 02 defines Recently Deleted as "tombstones that still have content", where `has_content` is "true when any of the emptied lists is non-empty". The two rules conflict for an item whose lists were always empty.
- **Observed:** an item with a title and tags but no fields, history, attachments or markers goes straight to a stripped tombstone when deleted. It is not in `deleted_items()`, and `recover` returns `Malformed("item … has no content")`. Such items arise from:
  - `vault add --title X`.
  - A CSV row with only a title: `import_csv` drops empty columns.
  - A KeePass entry with only a title.

  The app still shows "You can recover it … for 30 days" for them (`screens/main/prompts.rs:94`). The app's own test comment knows about the gap: "Only a tombstone with content is in the trash: give each item a field."
- **Why it matters:** the confirmation promises recoverability that does not exist. The title and tags are permanently out of reach, even though the format keeps them on the tombstone.
- **Reproduction:** `cd qa/spec-checks && cargo test --test trash -- tr06`
- **Suggested fix:** track "in the trash" explicitly instead of inferring it from content. For example, treat a tombstone whose `modified_at == deleted_at`, or one not restamped by a strip, as trashed; or add an optional `stripped_at` key (no format bump: optional key). Alternatively, skip the recoverability sentence for content-less items. Either way, record the choice in 02.

### L2. Content the KeePass parser rejects after a correct password is reported as wrong credentials

- **Severity:** low
- **Crate / location:** `vault-core`, `crates/vault-core/src/import/kdbx.rs:110-113`.
- **Expected:** 05 §2.5: "Incorrect credentials leave the prompt open for retry." D-8 introduced `ImportError::KdbxMalformed` so a damaged database is not mistaken for a wrong password.
- **Observed:**
  - Only a panic maps to `KdbxMalformed`. Every `Err` from `Database::parse` maps to `KdbxCredentials`.
  - A valid KDBX4 file with 200 or more nested groups opens with the right password but fails in the parser. It reports `[KdbxCredentials]`, exactly like a wrong password. Depth 100 imports fine.
  - The import walk itself is iterative and not the cause.
- **Why it matters:** the app keeps the password prompt open, and the user retries a correct password indefinitely. The message does mention possible damage, which softens this.
- **Reproduction:**
  ```
  cd qa/spec-checks && cargo build --bins && cargo test --test kdbx_hostile -- kh04 --nocapture
  ```
- **Suggested fix:** map the keepass error kinds. Key, HMAC and credential errors become `KdbxCredentials`; XML, inner-header and structure errors after authentication become `KdbxMalformed`.

### L3. The backup viewer reads `backups/` entries through symlinks

- **Severity:** low (code read only)
- **Crate / location:** `vault-app`, `crates/vault-app/src/screens/backup.rs:195` (`read_capped(&backup_file(&path), …)`), and the rationale at `crates/vault-app/src/bounded_read.rs:6-7`.
- **Expected:** 03 §2 "Not following links (D-1)": "every file the package opens (`.lock`, `vault.bin`, backups, blobs, conflict-copy sources) is opened with `O_NOFOLLOW` and must be a regular file after `fstat`; a symlink ... is `UnsafePackageEntry`, never a silent fallback".
- **Observed:**
  - `vault_sync::read_capped` follows symlinks. The comment justifies this because the path is "a backup row the user clicked, not one found by scanning a synced folder". But backup rows are found by scanning `backups/`, a synced folder.
  - `list_backups` skips a symlinked top-level entry. However, `vault.bin` inside an absorbed conflict package in `backups/` is listed even when it is a symlink (size 0), and the viewer then follows it.
  - `restore_from` uses the no-follow reader for the same files, so the two paths disagree.
- **Why it matters:** the impact is small: the target is parsed as a vault and a parse error is shown, with no disclosure, and FIFOs and devices are refused by `read_capped`. But it is a direct deviation from the D-1 rule, reachable with a sync client that syncs symlinks (Syncthing does).
- **Reproduction:** reading `screens/backup.rs:190-197` together with `vault-sync/src/synced.rs:1160-1176` (`read_capped`) and `backup.rs:335-344` (conflict-package size via `symlink_metadata`, entry still listed).
- **Suggested fix:** expose a no-follow variant (the existing `read_with_stat` / `open_regular`) for package-internal reads, and use it in the viewer.

## What held up

These checks passed on the inputs listed. They show the behaviour on those inputs; they are not proofs.

**Recently Deleted, core:**
- `delete` keeps fields, history, refs, `removed_fields` and `removed_attachments`, and the content survives serialize/parse (`tr01`).
- Search and tag filters exclude trashed items.
- `recover` restamps past a backwards clock and errors on an unknown id, a live item or a stripped tombstone (`tr02`).
- `delete_permanently`:
  - Empties all seven lists.
  - Keeps the title, tags, favorite, icon, `created_at`, `deleted_at` and the per-attribute stamps byte-for-byte.
  - Restamps, sets the device id, and refuses live or unknown items (`tr03`).
  - Drops item and record extras on every item of the `v1-forward` fixture (`tr04`).
- `expire_deleted`: strict cutoff, idempotent, no restamp on a no-op (`tr05`).
- **Merge:**
  - Strips propagate across three devices (`tr07`).
  - The recover-vs-strip race keeps the item live with its content in both orders, and a fresh delete afterwards trashes it again (`tr08`).
  - A same-millisecond both-tombstone tie with a cloned device id converges: content after one exchange, fully after two (`tr09`), as the roadmap's merge laws state.
  - Guarantee 9 holds with content, and an edit after a delete resurrects (`tr10`).
- **Corruption:** every cut offset and 600 bit flips over a file with a trashed and a stripped tombstone fail cleanly, with no silent change (`tr15`).

**Recently Deleted, sync and CLI:**
- Snapshots are not scrubbed, and `restore_from` brings the item back into the trash, not live (`tr12`).
- A trashed item's attachment stays referenced and readable, and its blob is kept within the 24 h grace (`tr13`).
- Two handles round-trip delete → recover → permanent delete (`tr14`).
- `vault rm` keeps the content on the tombstone (`tr16`).

**D-1 (symlinks and FIFOs):**
- A symlinked `.lock` (live or dangling) is refused with `UnsafePackageEntry`. Nothing is created through it and the vault stays dirty (`rf01`).
- A symlinked `vault.bin` is refused by vault-sync and the CLI (`rf02`).
- FIFOs as `vault.bin`, `.lock`, a per-file copy, a sibling package's `vault.bin` or a blob never hang the CLI (`rf03`).
- Symlinked `backups/` and `attachments/` receive nothing (`rf04`).
- A symlinked blob is not read (`rf05`).

**D-10 caps:**
- A 65 MiB primary or per-file copy is refused with a typed error, the primary is untouched and the copy is kept (`rf06`).
- A 70 MB attachment works end to end: add, open, and publication from a sibling conflict package (`rf08`), and also through the CLI.
- A 70 MiB KDBX imports within the 100 MiB limit (`kh02`).

**D-6 blob publication:** flipped-byte, short, long and swapped blobs are never published, while the good sibling blob is. An existing blob is never replaced, and no tmp files are left (`rf09`).

**D-11 watcher bounds:**
- The first poll absorbs at most 8 of 20 copies, and all are absorbed eventually (`rf10`).
- One `vault sync` merges and moves 300 per-file copies (`rf11`) and 20 copies (CLI).
- With 10 blob-waiting packages plus a per-file copy, `vault sync` terminates and merges all eleven (`rf16`).

**D-9 header tie-break:** a cloned device id with the same-millisecond `change_password`, `rotate_vault_key` or `add_enclave_slot` gives identical headers after one exchange, and both files open with one password (`rf12`).

**D-2 (`ReplaceIf`):**
- Five same-bytes, new-inode rewrites never block a save (`rf13`).
- Two handles × 25 saves in a tight loop lose nothing and surface no errors (`rf14`).

**D-7 (CLI `sanitize_line`):** these outputs carry no raw ESC, BEL or CR, and C1 and bidi controls are escaped too:
- `list`, `get`, `get --reveal`, `get --ids`, `attach list`, `list --tag` and the not-found error.
- A newline in a title does not forge a row.

**D-8:** in release builds, deep nesting returns a clean error at every depth up to 20,000 on 2 MiB and 8 MiB stacks.

**Dist parity:**
- The core checks pass identically with `--release`, including the `u64::MAX` stamp sweeps where overflow checks differ.
- `[profile.dist]` inherits release and keeps `panic = "unwind"`.
- The remaining `debug_assert!`s (`strip_tombstone`, `merge_items` id equality, opaque slot kind, generator class count, reconcile while locked) guard invariants their callers already enforce.

**Unlock screen (code read only):**
- `start_unlock_finish` computes `max(remaining − 150 ms, 200 ms)` with `remaining = 500 ms − E`, which equals spec 05's `D = max(350 ms − E, 200 ms)`.
- Failures and Reduce Motion wait out the 500 ms hold.
- Staleness is judged after the wait, through `lock_gen` and `epoch`, so a lock during hold or finish installs the vault locked and a switch drops it.
- The wheel's `finish_phase` lands on a sector boundary (frame 0) at 0.7·D and starts at the current speed.
- The keyhole envelope is smoothstep, full at 0.2, held to 0.6 and gone at 1.0.
- Touch ID: `NotAvailable` shows a toast without counting a failure; `BiometryChanged` and invalid enclave keys mark the enrolment stale; reboot, 7 days and 5 failures gate it; a failed `boot_time` read fails closed.

**Secrets:** no new `String` for secrets, and no log line with secret content, across the diffs in vault-core, vault-sync, vault-cli and vault-app. No new `unsafe` outside vault-macos.

**Project suite:** fmt and clippy are clean; 1077 tests passed.

## Notes (spec ambiguities, not counted)

- **Strip vs recovery can lose attachment blobs.** 03 §1.1 still says "Deleting an item keeps its refs on the tombstone until `purge_tombstones_older_than`, so the other device learns about the deletion before the blob can go." Since 2026-11-03, a strip drops the refs. Orphan cleanup's 24 h grace counts from when the blob arrived, not from when it lost its last reference, so a blob trashed for 30 days is deleted at the save right after the strip. In the owner-accepted recover-vs-strip race (03 §5) the item survives, but its attachments can show as Missing. The spec should say so, or cleanup should give a just-unreferenced blob its own grace.
- **Both-tombstone whole-item LWW** keeps only one side's pre-delete content. If two devices edited different fields and then both deleted, `recover` restores only the winner's edits. This follows the spec table, but it is weaker than the live-item field merge.
- **The trash sweep and vault-sync's own saves.** 05 §2.3 runs the sweep "before each autosave and lock-save". vault-sync's own write-back saves (03 §3 step 6c/e) are not preceded by it, so content a merge brings back past its window can reach disk until the next app save. The 03 §5 wording ("stripped again by the app's sweep before the next save") reads as if every save were covered.
- **CLI sanitising:**
  - A backslash is not escaped, so a value containing a literal `\n` or `\u{7}` prints the same as an escaped control character.
  - `sanitize_line` turns a tab into a space in revealed one-line values, so a revealed password containing a tab prints differently from what it is.

  Neither is specified.
- **Import caps:** the 64 MiB cap on CSV import (app and CLI) is not in the spec.
- **Debug-build stack:** in debug builds, the keepass parser overflows a 2 MiB thread stack on a 200-deep group tree (SIGABRT) before rejecting it; on 8 MiB it errors cleanly. Release is fine, so this is not a shipping issue. `kh01` uses 8 MiB in debug for this reason.
- **Error text with paths:** app error toasts for some `SyncError`s include the vault path (`other.to_string()`). This was already the case before this wave, and the path is the user's own.
- **Lock during the finish:** the accepted residual ("Unlocking…" stays up to 350 ms after a lock during the finish) matches the code.

## Limits

- vault-app and vault-macos cannot be driven here. M2, L3 and the unlock-screen, sweep-timing and Touch ID results are code read only. Visual behaviour (the wheel landing on frame 0, the keyhole halo, no card/main overlap on screen) was not observed.
- No two-Mac, iCloud or Dropbox run. The cloud providers were simulated with two handles on one folder and hand-made conflict copies of both shapes.
- The race between the `ReplaceIf` checks and rename(2) was not provoked. vault-sync's `before_checks` hook is crate-private.
- The orphan-cleanup timing after a strip was not exercised, because ctime cannot be aged.
- The KDBX sweeps cover the outer header, KDF parameters, truncation and nesting. The inner XML schema was not fuzzed.
- Release-mode parity was checked with `--release`, not with the `dist` profile (fat LTO). The project notes that vault-app UI tests need debug assertions under `dist`.
- A passing check shows the behaviour on the inputs tried. It is not a proof.
