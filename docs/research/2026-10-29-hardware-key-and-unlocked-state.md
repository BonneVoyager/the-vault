# Hardware second factor for the KEK, and security while unlocked on macOS

Research note, 2026-10-29. Research only; no code or spec changed. Every derivation below is a **proposal, needs owner approval**.

Owner's question: "In addition to a password, my KeePass database uses an extra key file and a challenge mechanism. Even if malware were to extract my database, they still wouldn't be able to open it, as they would lack the hardware key. Security at rest is one thing, but security during active use, when the database is unlocked, is quite another."

## Executive summary

1. Yes, the KeePassXC design is sound for the threat it addresses: an attacker who gets the file but not the YubiKey/key file cannot derive the key, because the challenge response (and key file hash) are inputs to the master key (KeePassXC `CompositeKey.cpp:85-107`, `135-160`).
2. It is *not* a second factor in the authentication sense and adds nothing while the vault is unlocked. KeePassXC's own FAQ says so: it "makes your password stronger, but technically it doesn't qualify as a separate second factor" ([KeePassXC FAQ, YubiKey/OnlyKey](https://keepassxc.org/docs/#faq-yubikey-2fa)).
3. Our format can add this without any new primitive: a new slot kind whose KEK is `HKDF-SHA256(ikm = Argon2id(pw) || hw_response [|| SHA256(keyfile)], salt = vault_id, info = "vault/slot/hw/v1")`. Argon2id, HKDF-SHA256 and XChaCha20-Poly1305 suffice.
4. Use a **static per-slot random challenge** stored in the slot, not KeePassXC's rotate-on-every-save challenge. Our slots are only touched at unlock, so rotating would require the hardware key on every save, which breaks the sync model. Rotation becomes an explicit "rotate hardware challenge" operation.
5. Adding a new slot kind **requires a FORMAT_VERSION bump** today: `vault-core/src/format.rs:386-387` rejects unknown kinds as `Malformed`, so a v1 reader could not open the file at all. Alternative: first ship a v1.x reader that skips unknown-kind slots, then add kinds without a bump.
6. A hardware factor makes a **recovery slot mandatory**: a lost or dead YubiKey otherwise means a lost vault. KeePassXC's answer is "program two YubiKeys with the same 20-byte HMAC secret and print the secret on paper".
7. Prefer FIDO2 `hmac-secret` over YubiKey HMAC-SHA1 where possible: credential-bound random secret, 32-byte HMAC-SHA-256 outputs, user presence/verification built in. Apple's `ASAuthorization` exposes a PRF input for passkeys since macOS 15 and for security keys only from macOS 26.4; a Rust app would otherwise talk CTAP over HID itself.
8. While unlocked, nothing stops malware running as the user: our `vault_key` and all decrypted items are in process memory (the Secure Enclave only does P-256 operations and cannot hold a symmetric key for us). Hardened runtime blocks `task_for_pid` from non-root debuggers and library injection; it is not a defence against root, and `NSWindowSharingNone` is now documented by Apple as a legacy constant that must not be relied on to hide content.
9. What actually limits damage during use: short auto-lock, zeroize on lock (already done), Touch ID re-auth before reveal/copy of high-value items, clipboard concealment plus `currentHostOnly`, no `get-task-allow`, and `mlock` of key material.
10. Recommendation for v2: add `kind = "hw"` slots (YubiKey HMAC-SHA1 and FIDO2 hmac-secret variants), optional key file mixing, a mandatory `recovery` slot when any `hw` slot exists, and the unlocked-state hardening in §2 below. Full list in "Recommendation for vault v2".

## Part 1 — Hardware or second factor for the KEK

### 1a. How KeePassXC composes password, key file and challenge-response

- Static keys (password, key file) are hashed with SHA-256 in insertion order; if a transform seed is supplied, the challenge-response result is appended to the same SHA-256 ([CompositeKey.cpp:85-107](https://github.com/keepassxreboot/keepassxc/blob/develop/src/keys/CompositeKey.cpp)).
- Challenge-response keys are challenged with the seed, each response (`key->rawKey()`) is hashed into a separate SHA-256 whose result is the "challenge result" (`CompositeKey.cpp:135-160`).
- For KDBX4 the challenge is the **KDF seed** (`kdf.seed()`), not the master seed: `CompositeKey::transform` passes `kdf.seed()` into `rawKey(&seed, ...)` (`CompositeKey.cpp:122-133`). The KDBX3 path uses the master seed instead via `Database::challengeMasterSeed` (`Database.cpp:909-928`, called from `Kdbx3Writer.cpp:49`).
- The seed is re-randomised on every save: `Kdbx4Writer::writeDatabase` calls `db->setKey(db->key(), false, true)` (`Kdbx4Writer.cpp:51`), and `updateTransformSalt == true` calls `m_data.kdf->randomizeSeed()` (`Database.cpp:965-968`). So each save needs a fresh response from the device, which is why KeePassXC prompts for a touch on save. The final key is `SHA-256(masterSeed || transformedKey)` (`Kdbx4Writer.cpp:57-61`, `Kdbx4Reader.cpp:59-61`); the HMAC key is `SHA-512(masterSeed || transformedKey || 0x01)` (`KeePass2.cpp:55-62`), matching the KeePass KDBX 4 doc's "512-bit key derived from the user's master key and the master seed" ([kdbx_4.html](https://keepass.info/help/kb/kdbx_4.html)).
- Consequence stated by the FAQ: the expected response "doesn't change every time you try to decrypt your database. It does, however, change every time you save your database... the previous version of your database can still be decrypted with the old challenge/response" ([FAQ](https://keepassxc.org/docs/#faq-yubikey-2fa)).
- The YubiKey driver pads the challenge to 64 bytes with PKCS7 and truncates the response to 20 bytes: "actual HMAC-SHA1 response is only 20 bytes" ([YubiKeyInterfaceUSB.cpp](https://github.com/keepassxreboot/keepassxc/blob/develop/src/keys/drivers/YubiKeyInterfaceUSB.cpp)).
- Backup practice: "It is advisable to have a backup replica YubiKey... The same HMAC key will need to be written to both keys", using `ykpersonalize -2 -a -ochal-resp -ochal-hmac -ohmac-lt64 -oserial-api-visible -oallow-update`, and "storing your HMAC key in a safe place (e.g., printed on paper)" ([User Guide, Creating a YubiKey backup](https://keepassxc.org/docs/KeePassXC_UserGuide#_creating_a_yubikey_backup)).
- Loss: for key files the FAQ is explicit, "If you lose your key file, you lose your database"; the same follows for a YubiKey without a replica, since the response is an input to the key.

### 1b. Key file formats KeePassXC accepts

From [FileKey.cpp](https://github.com/keepassxreboot/keepassxc/blob/develop/src/keys/FileKey.cpp), tried in order:

| Format | Key bytes |
|---|---|
| XML v1 (`Version` 1.0) | Base64 `Data`, truncated to 32 bytes, no checksum |
| XML v2 (`Version` 2.0) | hex `Data`, verified against `Hash` = first 4 bytes of SHA-256 ("Checksum mismatch! Key file may be corrupt.") |
| Fixed binary, exactly 32 bytes (deprecated) | used verbatim |
| Hex, exactly 64 chars (deprecated) | hex-decoded |
| Anything else | SHA-256 of the whole file |

Guidance: "a key file can be very strong additional protection if kept separately from the database file, such as on an external thumb drive. If you sync your database via a cloud provider... you should only sync the KDBX file and distribute the key file to your computers by different means" ([FAQ, Key Files](https://keepassxc.org/docs/#faq-keyfile-howto)). Same FAQ: "never use a key file without an actual password".

### 1c. Known weaknesses of YubiKey HMAC-SHA1, and the FIDO2 alternative

- The slot holds a **20-byte shared secret** programmed from the host: "The key must be 16 bytes in size for Yubico OTP or 20 bytes for HMAC-SHA1", and it "must also be provided to the validation server" in the authentication use case ([Yubico SDK: program a challenge-response credential](https://docs.yubico.com/yesdk/users-manual/application-otp/how-to-program-a-challenge-response-credential.html)). Whoever saw it at programming time (the host, a backup paper) owns the factor. Compromise of the secret equals compromise of the factor, and KeePassXC's backup practice deliberately keeps a copy of it.
- After programming the secret is not readable: "Secrets cannot be extracted from the YubiKey once configured" ([Yubico SDK: challenge-response](https://docs.yubico.com/yesdk/users-manual/application-otp/challenge-response.html)).
- Challenge up to 64 bytes, response 20 bytes (same page). `ykman otp chalresp` offers `--touch` ("Require touch on the YubiKey to generate a response") and `--generate` ([ykman OTP commands](https://docs.yubico.com/software/yubikey/tools/ykman/OTP_Commands.html)). Without `--touch` any process that can open the USB HID device gets a response silently.
- No attestation: the OTP applet's HMAC-SHA1 slot has no per-device key pair or certificate the host can verify. Unsourced as a negative statement; nothing in the Yubico OTP documentation above offers one.
- SHA-1: RFC 6194 §3.3, "there is no indication that attacks on SHA-1 can be extended to HMAC-SHA-1" ([RFC 6194](https://www.rfc-editor.org/rfc/rfc6194)). The 20-byte secret and output are the real limit, not the hash.
- **FIDO2 `hmac-secret`** (CTAP 2.1 §12.5): "used by the platform to retrieve a symmetric secret from the authenticator... scoped to a credential"; at `makeCredential` the authenticator "generates two random 32-byte values (called CredRandomWithUV and CredRandomWithoutUV)"; at `getAssertion` the platform sends one or two 32-byte salts encrypted under the PIN/UV shared secret and gets back `output1: HMAC-SHA-256(CredRandom, salt1)` (32 bytes), with `CredRandomWithUV` chosen when the uv bit is set; `up=false` returns `CTAP2_ERR_UNSUPPORTED_OPTION`, so user presence is mandatory ([CTAP 2.1 §12.5](https://fidoalliance.org/specs/fido-v2.1-ps-20210615/fido-client-to-authenticator-protocol-v2.1-ps-20210615.html#sctn-hmac-secret-extension)). The secret never leaves the key, is generated on the key, and is per credential; this fixes the three HMAC-SHA1 weaknesses above. Backup still needs a second credential on a second key and therefore a recovery slot.
- **macOS native path**: `ASAuthorizationPublicKeyCredentialPRFAssertionInput` is "input for the web authentication PRF extension in passkey assertion requests", macOS 15.0+ ([Apple](https://developer.apple.com/documentation/authenticationservices/asauthorizationpublickeycredentialprfassertioninput)). The security-key request `ASAuthorizationSecurityKeyPublicKeyCredentialAssertionRequest` gains a `prf` property only at **macOS 26.4** ([Apple](https://developer.apple.com/documentation/authenticationservices/asauthorizationsecuritykeypublickeycredentialassertionrequest)). On our macOS 14 floor the native API is unavailable, so a Rust app must speak CTAP2 over HID itself (crates in 1e).

### 1d. Mapping onto our format with only Argon2id, HKDF-SHA256, XChaCha20-Poly1305

Proposal, needs owner approval:

```
slot.kind        = "hw"
slot.hw          = "yubikey_hmac_sha1" | "fido2_hmac_secret"
slot.challenge   = bytes(32)   random per slot (OsRng), static
slot.keyfile     = bool        whether SHA256(keyfile) is mixed in
slot.device_hint = tstr        serial (YubiKey) or credential_id hex (FIDO2); UX only, not secret
slot.credential_id = bytes     FIDO2 only; needed for allowList
slot.rp_id       = tstr        FIDO2 only, e.g. "vault.local"

hw_response = YubiKey: HMAC-SHA1(slot_secret, challenge padded to 64)      → 20 bytes
              FIDO2:   hmac-secret output1 with salt1 = slot.challenge      → 32 bytes
ikm         = Argon2id(password_nfc, kdf.salt, m, t, p)   (32 bytes, as today)
              || hw_response
              || SHA256(keyfile_bytes)     (only if slot.keyfile)
KEK         = HKDF-SHA256(ikm, salt = vault_id, info = "vault/slot/hw/v1")  → 32 bytes
wrapped_key = XChaCha20-Poly1305(KEK, nonce, vault_key, AAD = magic||version||vault_id||slot.id||"hw")
```

- Argon2id stays password-only so the KDF calibration and cost semantics of spec 01 §6 do not change; the hardware response and key file are mixed by HKDF, which is designed for concatenated non-uniform ikm. No new primitive. If the owner wants the response inside the Argon2id input instead (KeePassXC style), that also needs no new primitive; HKDF after Argon2id is simpler to reason about and lets each factor be an independent 32-byte-ish contribution.
- The `challenge` and `device_hint` are plaintext header fields. The challenge is not secret in either design (KeePassXC's seed is plaintext in the KDBX header too).
- **Static vs rotating challenge.** KeePassXC rotates because KDBX re-derives the whole database key on every save anyway, so the touch costs nothing extra in their model. Our slots are untouched by item writes; rotating would mean re-wrapping the slot, hence a hardware touch, on every autosave and on every merge the watcher performs, and a second device writing the file would need the key too. Static is the only fit. What static gives up: an attacker who once recorded a response (USB sniffing, or malware present at an earlier unlock) can replay it against any later copy of the file; with rotation a recorded response only opens the versions saved with that seed (FAQ above). What static does not give up: the owner's stated threat (malware exfiltrates the file, has no key) is defeated equally. Malware able to record the response at unlock time is on an unlocked host and can read `vault_key` from memory anyway (Part 2), so the marginal protection of rotation is small. Mitigations: require touch (`--touch` / FIDO2 user presence) so no response exists without a physical press; offer "rotate hardware challenge" as an explicit operation like password change; use hmac-secret with `salt2` to roll over in one touch when rotating.
- **Versioning.** Spec 01 §9 says optional CBOR keys are not a bump, but a new `kind` value is not an optional key: `format.rs:386-387` returns `Malformed("slot.kind: unknown kind")`, so any v1 build would refuse the whole file. Options: (i) bump `FORMAT_VERSION` to 2 with a fixture `v2-hw.vault`; (ii) first ship a v1.x reader that tolerates unknown kinds (skip the slot), wait for it to be deployed, then add `hw` without a bump. (i) is honest and simple.
- **Recovery slot.** With `hw` present, a `password` slot must be removed (otherwise the factor is cosmetic), and the `enclave` slot may stay (its KEK is device-bound in the Keychain and does not help a file-only attacker). Then loss of the hardware key is loss of the vault unless a `recovery` slot exists: KEK = `HKDF-SHA256(ikm = recovery_key (32 random bytes shown once as base32), salt = vault_id, info = "vault/slot/recovery/v1")`, same wrap. Creating an `hw` slot should force creating a `recovery` slot in the same flow. This mirrors KeePassXC's "print the HMAC secret" advice without exposing the hardware secret.
- Key file: store only `keyfile: true` in the slot; the path lives in app preferences, never in the header, so the file is not advertised next to the vault. Generate 32 random bytes; accept arbitrary files hashed with SHA-256 like KeePassXC's fallback.

## Part 2 — Security while unlocked on macOS

### 2a. What a Rust process can and cannot do

- `zeroize`: "guarantees the zeroing operation can't be 'optimized away' by the compiler" via `write_volatile` and fences, but "cannot guarantee copies of the data were not previously made by buffer reallocation", "stack spilling and other optimizations may leave temporary copies", and swap is "explicitly out-of-scope for this crate" ([docs.rs/zeroize](https://docs.rs/zeroize/latest/zeroize/)). We already use `Zeroizing<[u8;32]>` for keys (`crypto.rs:32`) and `UnlockedVault` redacts `Debug` (`vault.rs:321-333`); `export.rs:11-12` documents a known unzeroized `csv::Writer` buffer.
- `secrecy`: makes access "explicit and easy-to-audit", prevents "accidental leakage of secrets via channels like debug logging", and "does not provide more advanced memory protection mechanisms" such as `mlock`/`mprotect` ([docs.rs/secrecy](https://docs.rs/secrecy/latest/secrecy/)). It is API hygiene, nothing more.
- `mlock(2)` on macOS: locked pages "will cause neither a non-resident page nor address-translation fault until they are unlocked"; limited by "the minimum of a system-wide 'wired pages' limit and the per-process RLIMIT_MEMLOCK"; "Locked mappings are not inherited by the child process after a fork" (`man 2 mlock`, macOS 27.0.1). On this machine `ulimit -l` is `unlimited` and `vm.swapusage` reports `(encrypted)`. Hibernation: `hibernatemode = 3 by default on portables. The system will store a copy of memory to persistent storage` (`man pmset`); the man page does not say whether `mlock`ed pages are excluded from that image, and whether the image is encrypted beyond FileVault's volume encryption is **unsourced**. `MAP_NOCACHE` affects the file cache, not secrecy; irrelevant.
- **Secure Enclave cannot hold `vault_key`.** Apple: the Secure Enclave "Works only with NIST P-256 elliptic curve keys. These keys can only be used for creating and verifying cryptographic signatures, or for elliptic curve Diffie-Hellman key exchange (and by extension, symmetric encryption)" and "Can't encode preexisting keys" ([Protecting keys with the Secure Enclave](https://developer.apple.com/documentation/security/protecting-keys-with-the-secure-enclave)). Our XChaCha20 key must therefore be in process memory to decrypt items; the SE can only wrap/unwrap it (spec 04 §2, via `SecKeyCreateDecryptedData`, [Apple](https://developer.apple.com/documentation/security/seckeycreatedecrypteddata(_:_:_:_:))).
- Keychain: `kSecAttrAccessibleWhenUnlockedThisDeviceOnly` means "accessed only while the device is unlocked by the user" and items "do not migrate to a new device" ([Apple](https://developer.apple.com/documentation/security/ksecattraccessiblewhenunlockedthisdeviceonly)); with `biometryCurrentSet` the SE key is usable only after biometry. Apple's own caveat applies to anything returned: "to use the key, you must briefly copy a plain-text version of it into system memory... if your app is compromised, the key could also become compromised" (Secure Enclave page above).

### 2b. Hardened runtime and entitlements

- Apple: "The Hardened Runtime, along with System Integrity Protection (SIP), protects the runtime integrity of your software by preventing certain classes of exploits, like code injection, dynamically linked library (DLL) hijacking, and process memory space tampering" ([Hardened Runtime](https://developer.apple.com/documentation/security/hardened-runtime)). Required for notarization.
- Keep **absent**: `com.apple.security.cs.disable-library-validation` (library validation "prevents a program from loading frameworks, plug-ins, or libraries unless they're either signed by Apple or signed with the same Team ID" ([Apple](https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.security.cs.disable-library-validation))); `com.apple.security.cs.allow-dyld-environment-variables` ("which you can use to inject code into your app's process" ([Apple](https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.security.cs.allow-dyld-environment-variables))); `com.apple.security.get-task-allow` ("poses a security risk for a shipping app, because it can allow an attacker to inject code at runtime"; notarization fails with "The executable requests the com.apple.security.get-task-allow entitlement" ([Resolving common notarization issues](https://developer.apple.com/documentation/security/resolving-common-notarization-issues))).
- What it buys against memory reading: "even with the debugging tool entitlement, a debugger can't get the task ports of processes that don't have the Get task allow entitlement, and that are therefore protected by System Integrity Protection"; non-root debuggers also face an admin authorization dialog ([cs.debugger](https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.security.cs.debugger); `man 8 taskgated`).
- **Root**: SIP "restricts the root user account and limits the actions that the root user can perform on protected parts of the Mac operating system", i.e. `/System`, `/usr`, `/bin`, `/sbin`, `/var` and Apple apps ([About SIP](https://support.apple.com/en-us/102149)). Nothing in Apple's SIP or hardened-runtime documentation claims to protect a third-party process's memory from a root attacker, and root can install launch daemons, replace our binary on disk, or disable SIP from recovery. Treat "root malware cannot read our memory" as **unsupported**; the honest statement is that hardened runtime raises the bar for user-level injection and debugger attach, not for root.

### 2c. Screen capture

- KeePassXC sets `[window setSharingType: NSWindowSharingNone]` ([AppKitImpl.mm:233](https://github.com/keepassxreboot/keepassxc/blob/develop/src/gui/osutils/macutils/AppKitImpl.mm)) and documents that it "prevents recordings and screenshots of the application window on Windows and macOS" ([User Guide, Screenshot Security](https://keepassxc.org/docs/KeePassXC_UserGuide#_screenshot_security)).
- Apple's current documentation for `NSWindow.SharingType.none` reads: "A legacy constant that macOS no longer uses. `NSWindowSharingNone` can cause content to not be available in certain sharing situations. Don't use this value to hide or omit content from being captured. Instead, use FairPlay Streaming (FPS)" ([Apple](https://developer.apple.com/documentation/appkit/nswindow/sharingtype-swift.enum/none)). `readOnly` is "The window's contents can be read but not modified by another process". So Apple no longer guarantees that `sharingType = .none` blocks ScreenCaptureKit; on which macOS versions it still has effect is **unsourced**. It remains cheap to set as best effort, but must not be described as protection.
- gpui 0.3.10 exposes no `sharingType` API (grep of the vendored source); vault-macos would set it on the `NSWindow` handle via objc2. `NSSecureTextField` semantics (no autocomplete, no text services, not readable by Accessibility/AppleScript, no undo buffer) are unavailable in gpui's own text input; what we lose is the OS-level exclusion of the password field's content from the accessibility tree and input-method pipeline. **Unsourced** beyond AppKit class naming; Apple's page for `NSSecureTextField` was not fetched.

### 2d. Clipboard

- nspasteboard.org defines `org.nspasteboard.ConcealedType` ("content that should be treated as confidential... Avoid recording it to a file, or consider encrypting it"), `org.nspasteboard.TransientType` ("content will be on the pasteboard only momentarily... should not be recorded or displayed in a pasteboard history"), `org.nspasteboard.AutoGeneratedType`, and lists Apple's `com.apple.is-remote-clipboard` as a marker "for identifying pasteboard content copied from another device ('Handoff')" ([nspasteboard.org](http://nspasteboard.org/)). These are a convention honoured by clipboard managers; they do not control Universal Clipboard.
- Apple: "The general pasteboard... automatically participates with the Universal Clipboard feature in macOS 10.12 and later... There is no macOS API for interacting with this feature" ([NSPasteboard](https://developer.apple.com/documentation/appkit/nspasteboard)). However `NSPasteboard.ContentsOptions.currentHostOnly` (macOS 10.12+) means "The pasteboard contents are available only on the current device, and not on any other devices" ([Apple](https://developer.apple.com/documentation/appkit/nspasteboard/contentsoptions/currenthostonly)), passed to `prepareForNewContents(with:)`. Spec 04 §3 should add `currentHostOnly` alongside `ConcealedType`; iOS's equivalent is `UIPasteboard.OptionsKey.localOnly`.

### 2e. Threat model honesty: malware running as the user on an unlocked session

| Attacker capability | Can still | Stopped by hardware key? | What actually limits it |
|---|---|---|---|
| Read our memory (`task_for_pid` with debugger entitlement + admin auth, or root) | take `vault_key` and every decrypted item | No | Short auto-lock; zeroize on lock (done, `vault.rs:767`); `mlock`; no `get-task-allow` |
| Inject code (dylib, `DYLD_*`) | same as above | No | Hardened runtime, library validation (2b) |
| Screen-scrape | read whatever is shown | No | Per-item reveal, masked fields, best-effort `sharingType` |
| Keylog | capture the master password at next unlock | No (it still needs the key to use it offline; with touch-required it also needs a press) | Touch ID unlock avoids typing; hardware factor with touch |
| Read pasteboard | copied password for up to 30 s | No | ConcealedType, auto-clear, `currentHostOnly` |
| Exfiltrate the file only | nothing without password **and** hardware key | **Yes** | This is the one case the factor is for |
| Call our IPC | n/a, v1 has no IPC or extension | n/a | Keep it that way until a reviewed design exists |

Decrypt-lazily trade-off: `UnlockedVault` holds `items: BTreeMap<Uuid, Item>` fully decrypted (`vault.rs:311`). Keeping ciphertext and decrypting on demand would shrink the window for a memory read, but search needs titles, usernames and URLs in memory, and `item_key` must stay resident to decrypt anything, so an attacker who can read memory still gets the key and can decrypt all records from the file. Lazy decryption buys little against a memory reader; it mainly reduces what a partial dump or a crash log contains. A cheaper win is **re-authentication for reveal/copy** of items the user marks high-value (Touch ID via `LAContext`, not a crypto boundary, but a prompt the user sees).

### 2f. What 1Password and KeePassXC do during use

- 1Password: "1Password only decrypts your secrets in memory and never writes decrypted secrets to disk"; "the issue described in the report is only a threat to a computer that is already compromised"; "Lock your computer when you're not using it" ([Managing 1Password secrets in memory](https://support.1password.com/kb/201902a/)). The Security Design White Paper's "Beware of the Leopard" section says malware "that can inspect the memory of your computer or device when the 1Password client has unlocked your data" can extract secrets, and that once malware has that power nothing can in principle protect other processes (quoted by 1Password staff at [1password.community](https://www.1password.community/1password-at-home-31/security-model-of-unlocked-1password-desktop-app-in-offline-mode-passkey-specific-attack-25031); white paper PDF: https://1passwordstatic.com/files/security/1password-white-paper.pdf, section not re-read directly here).
- KeePassXC security settings ([ApplicationSettingsWidgetSecurity.ui](https://github.com/keepassxreboot/keepassxc/blob/develop/src/gui/ApplicationSettingsWidgetSecurity.ui), string lines 155-236): "Lock databases after inactivity of", "Lock databases when session is locked or lid is closed", "Lock databases when switching user", "Lock databases after minimizing the window", "Clear clipboard after", "Hide passwords in the entry preview panel", "Hide TOTP in the entry preview panel", plus "Enable database quick unlock (Touch ID / Windows Hello)". Quick Unlock stores credentials for biometric re-unlock; "If you are using a hardware key (e.g. YubiKey), it must be connected to your computer to complete the unlock" ([User Guide, Quick Unlock](https://keepassxc.org/docs/KeePassXC_UserGuide#_quick_unlock)). Our spec 00/04 already covers idle lock, screen-lock and sleep lock; "lock on user switch" and "lock on minimize" are not in our spec.

## Recommendation for vault v2 (proposal, needs owner approval)

1. **Spec 01 §2**: new `kind = "hw"` with fields `hw`, `challenge` (32 bytes), `keyfile` (bool), `device_hint`, and for FIDO2 `credential_id` and `rp_id`. Bump `FORMAT_VERSION` to 2, add fixture `tests/fixtures/v2-hw.vault` with a fixed fake response in the test (no hardware in CI), and make the reader tolerate unknown slot kinds from v2 on so v3 kinds need no bump.
2. **Spec 01 §3**: KEK derivation for `hw` and `recovery` slots exactly as in 1d, HKDF info strings `vault/slot/hw/v1` and `vault/slot/recovery/v1`. `vault-core` gains `add_hw_slot(response_provider, keyfile_hash)` and `unlock_with_factors(...)`; the device I/O lives in `vault-macos` behind a `HardwareFactor` trait so core stays I/O-free.
3. **Invariant**: when an `hw` slot exists, no `password` slot may exist and at least one `recovery` slot must exist. Enforce in `vault-core`, test it.
4. **Device support order**: FIDO2 hmac-secret over CTAP HID first (credential-bound secret, touch mandatory), YubiKey HMAC-SHA1 second for KeePass migrants; require the touch option when programming a slot from our UI (`ykman`-equivalent config via the chosen crate or instruct the user).
5. **UX**: enrol flow = unlock with password → insert key → touch → show recovery key once → confirm → write slots atomically. Unlock = password + touch. "Rotate hardware challenge" in settings. Show `device_hint` so the user knows which key to insert.
6. **Unlocked-state hardening (spec 04/05)**: `mlock` the `Keys` struct and the KEK buffers in `vault-core` via a small `vault-macos` hook (core may not call libc); keep `get-task-allow` and both injection entitlements absent in `package.sh` and assert it in a test on the signed bundle; set `NSWindow.sharingType = .none` best-effort with a code comment citing Apple's "legacy" note; add `currentHostOnly` to `Clipboard::write_concealed`; add "lock on user switch"; add optional Touch ID re-auth on reveal/copy for items tagged high-value.
7. **Documentation**: spec 00 threat model gains a sentence that the hardware factor protects the file at rest and in transit only, and is deliberately not an unlocked-state control.
